### 1. SFT 冒烟测试与分隔符 bug

- 第一次冒烟（`runs/1030-smoke-*`）两条标准都过了：lr=0 跑 20 步后 dev200 与 base 完全相同（9.0%，McNemar 0/0）；lr=1e-4 loss 下降。

  1. 拆 loss：TinyGSM 预训练数据（不在 SFT 数据里）上的 loss 也降了约 5 倍——20 步不可能真的学到这么多，说明是格式问题；

- 教训（02「已更正的判断」）：lr=0 的冒烟标准查不出数据格式错误；训练分布要和 checkpoint 里实际保存的配置比，而不是和 yaml 默认值比。

- **训练正确率**（同题同序配对）：每个窗口都比 base 出发的格式分臂低约 2–6pp（例如第 76–100 步 0.217 vs 0.272）。
- **初步解读**（未核实）：
  - SFT 把 T=1 下的分布压窄、出错更多，RL 在 T=1 下没能补回来；低温下两条路线终点相同。
  - SFT 起点的 log-prob 本来就更低（−0.12 vs −0.106）、语法错误更多，更早走进不稳定区。
  - 题目要的"base → SFT → RL"这条路线，在这里不比"base → RL"好，T=1 下还更差。

### 第三轮 ②：base 格式分臂跑满 300 步（`runs/1031-grpo-base-fmt0.1-s300`，D34，第 174 步刹车）

- **配置**：与 D5 格式分臂完全相同（同 seed、同题序），上限从 150 改为 300。11-01 23:55–约 03:00 训练，之后跑 dev1000 确认，03:37 流水线结束并按计划关机。
- **刹车**：第 174 步触发（最近 10 步 log-prob 平均 −0.215 < 阈值 −0.210）。
  - 第 126–150 步还健康（log-prob −0.084，语法错 1.5%）；第 151–174 步 log-prob −0.18、语法错 5.1%。
  - 与二值臂对照：二值臂第 151–175 步已到 −0.27。所以格式分让发散**推迟**了约 25–30 步，但**没有防住**。
  - 结论：**只用格式分，300 步跑不下来**。这就补上了 Q42 里缺的对照。
- **dev200**（T=1 / T=0.1，两温度平均）：第 25 步 23.5 / 39.0（31.25），50 步 23.0 / 40.5（31.75），75 步 25.5 / 41.5（33.5），100 步 26.5 / 43.5（35.0），**125 步 30.0 / 44.5（37.25，最高）**，150 步 25.5 / 44.5（35.0），刹车步 174 步 24.5 / 41.5（33.0）。按规则选第 125 步，与 `select_grpo.pick` 的输出一致。
- **dev1000（第 125 步）**：T=1 30.6（后 800 题 30.8），T=0.1 46.4（46.9），都 p < 1e-5。
- **同配置跑两次**（本次 vs D5 格式分臂，按步配对）：
  - 训练正确率：第 1–150 步平均 0.226 vs 0.246；dev200 每个点低 1–5pp；

  - 这是 §4.1 的第一个实测样本：跑与跑之间的差异在 dev200 上可见（会影响选哪一步），在 dev1000 上落回噪声。

### 第二轮：格式分 + KL（`runs/1031-grpo-base-fmt0.1-kl0.04`，R41，300 步，未触发刹车）

## D4 RL 调试结果（10-30 晚，`runs/1030-D4-grpo-summary.md`）

设置见 02 D31。5 组都从 base 出发，各 50 步，32 题 × G=8，rollout 128 步 T=1；每 10 步 dev200 评测（base 参照：T=1 21.5%，T=0.1 39.0%，即同协议 dev1000 的前 200 题，已核对逐字相同）。

| 组 | dev200 T=1（10–50 步） | dev200 T=0.1（10–50 步） | 50 步权重变化 |
|---|---|---|---|
| lr 1e-6，二值，有 std | 21.0 / 21.5 / 21.0 / 21.0 / 21.0 | 39.5 / 40.0 / 39.0 / 40.0 / 39.5 | 0.0045% |
| lr 3e-6，二值，有 std | 22.0 / 21.5 / 21.5 / 22.5 / 21.5 | 40.0 / 40.5 / 38.5 / 40.0 / 39.0 | 0.014% |
| lr 1e-5，二值，有 std | 22.0 / 21.5 / 21.5 / 22.0 / 21.0 | 39.5 / 39.5 / 39.5 / 39.0 / 39.0 | 0.045% |
| lr 3e-6，二值，无 std | 21.5 / 22.0 / 22.0 / 21.5 / 22.5 | 40.0 / 40.5 / 39.5 / 40.0 / 40.0 | 0.013% |

- **模型几乎没动**：每个评测点与 base 只差 0–5 题（p ≥ 0.25）。参照：SFT lr 1e-5 第 1 个 epoch 权重变化 0.12% 时行为已明显改变，lr 1e-4 第 1 个 epoch 0.66%。权重变化与 lr 成正比。
- **训练奖励曲线 5 组几乎重合**（如第 1–10 步 0.143 / 0.141 / 0.142 / 0.144 / 0.142）：各组题目顺序相同（同 seed），模型几乎不变，曲线反映的是每批题的难度。好处是不同组可以按步配对比较。
- **每步样本利用率**：二值奖励每步约 47% 的 rollout 在"有对有错"的组里（约 120 / 256）；格式分约 93%（231–242 / 256），因为全错组里也有"能跑 vs 报错"的差别。
- **管线是对的**（`tests/test_grpo_direction.py`，16 题 × 8，lr 1e-4 同一批更新 5 次）：正优势轨迹 log π 平均 +1.48（85% 上升），负优势 −6.7（88% 下降），变化几乎都在答案词上。
- **固定 8 题过拟合检查**（`runs/1030-grpo-overfit8-lr1e-4`，lr 1e-4，30 步）：奖励 0.22 → 0.20 → 0.245（每 10 步平均），没有明显上升，但也没崩（动作 log-prob 稳定在约 −0.058）。
- **速度**：GPU 独占时每步约 38 秒（rollout 34 秒 + 训练 3.4 秒），每组 50 步加 5 次评测约 46 分钟。
- **结论 → D32**：学习率太小、每批 rollout 只用一次太浪费。正式跑用 lr 3e-5、每批更新 4 次（clip 生效），两臂对比格式分。三条判断更正见 02「已更正的判断」。

## D1 结果分析（10-30）

### 1. 新采样器验证（04 §2.4）

| 层次 | 结果 | 结论 |
|---|---|---|
| ① 逐字一致 | 16 组 token 完全相同；快路径与全量前向 token 100% 相同、log-prob 差 0 | 通过 |
| ② 统计一致 | dev200，256 步，T=1：原版 15.5%（31/200）vs 新版 17.0%（34/200），配对 McNemar p=0.77（只有新版对 24 题，只有原版对 21 题） | 通过 |
| ③ 收益 | 同设置 batch 64：原版 153 s / 峰值 47 GB；新版 76 s / 5 GB。新版 batch 200：67 s / 7.8 GB | **A800 上快约 2 倍，显存降到约 1/6–1/9** |

- 提速只有 2 倍，低于 04 按 4090 估的 3–4 倍：A800 的 FP64 强，原版的 float64 开销本来就不大，剩下的主要是模型前向。已记进 02「已更正的判断」。
- 实测单价：新采样器 dev 1000 × 256 步 = 277 s，约 **1.08 ms / (序列·步)**（A800，batch 200）；05 按 4090 估的是 1.25 ms。

### 2. 复现（test，1024 步，T=1）

- 15.92% [14.0, 18.0]，论文 18.0。单次评测的标准误约 1.0pp，2.1pp 的差距约等于 2 个标准误，**偏低但还在噪声范围的边缘**。
- 可能原因（都没核实）：seed 不同带来的采样方差；论文可能报告的是多 seed 或 bootstrap 均值；论文环境（torch 2.7、NGC 容器）里 `torch.compile` 和随机数实现与我们不同。
- 报告里如实写"复现值 15.9%，论文 18.0%"。这个值只用来对齐论文，后面所有对比都用我们自己测的 base。

### 3. dev 上的步数 × 温度扫描（新采样器，dev 1000）

| 步数 | T=1.0 | T=0.1 | 耗时 |
|---|---|---|---|
| 64 | 10.4% | 33.6% | 84 s |
| 128 | 14.3% | 36.2% | 148 s |
| 256 | 15.6% | 36.9% | 275 s |
| 512 | 17.8% | 38.8% | 532 s |
| 1024 | 17.5% | 38.1% | 1050 s |

相邻步数的配对 McNemar 检验：
- T=1：只有 64 → 128 显著（p=0.003）；128 → 256 p=0.39，256 → 512 p=0.14，512 → 1024 p=0.89；256 vs 1024 p=0.22。
- T=0.1：所有相邻对都不显著（p ≥ 0.13）；256 vs 1024 p=0.52。

读法：
- **步数**：128 步以后基本到平台，512 和 1024 没有区别。256 比 1024 低约 1–2pp，但不显著；耗时只有 1/4。
- **温度**：T=0.1 把准确率从约 17% 提到约 38%，翻了一倍多，和论文 Fig 3（T=0.1 约 33）方向一致，我们的数还更高。这意味着 **RL 的提升必须和"降温后的 base"比**（D16 的免费对照组），否则会把降温的效果算到 RL 头上。
- **错因**（256 步）：T=1 时 1000 题里 397 题代码执行报错或超时、447 题能跑但答案错；T=0.1 时报错降到 148 题、答案错 483 题。**降温主要修好的是"代码跑不起来"**，推理错误基本没少。这对 SFT / RL 的设计有用：base 在低温下的瓶颈是推理，不是格式。
- **dev 与 test 的差距**（04 §3.5）：1024 步、T=1 下 dev 17.5% vs test 15.9%，差 1.6pp。两个集合不同、不能配对，差值的标准误约 1.6pp，**不显著**。"dev 更简单"的担心目前证据不足，但 dev 仍然只用于相对比较。

### 实现说明（供下次接手）

- `fast_sampler.py` 三个开关：
  - `logits_mode=full`：和原版一样全量前向，再取出被选中的位置（逐字测试用）；`selected`：只在被选中的位置过输出层（正式用）。
  - `noise_mode=reference`：按原版的随机数消耗顺序生成全量 Gumbel 噪声，只用于逐字测试；`fast`：先抛硬币，只给选中位置生成噪声。
  - `skip_unchanged`：缓存隐状态，只对画布变了的序列重新前向（D07 的第二项优化，默认关）。
- 和原版的一处行为差异：某一步没有任何位置被揭开时，原版仍做一次前向，新版跳过。NFE 统计不同，生成分布不变。
- 逐字测试关掉了 `torch.compile`（`torch._dynamo.config.disable = True`）：原版 `sample_absorbing_posterior` 被 `torch.compile` 包着，编译后的 kernel 生成随机数的方式和 eager 不同，A800 上实测即使设 Inductor 的 `fallback_random=True` 也对不上（第一次测试 16 组全部"失败"就是这个原因，不是采样器的 bug）。算术相同，编译路径由层次 ② 的统计检验覆盖。
- AutoDL 把 `OMP_NUM_THREADS` 设成 0，libgomp 会报错，评测脚本里强制设成 8。
- 评测脚本：生成结果放在 `runs/<名称>/samples/`（不进 git），`metrics.json` 里存准确率、CI、耗时、显存峰值和每题对错字符串（以后做配对检验用）。
- 上游 `get_gsm8k_test_dataset` 的缓存目录只跟 tokenizer 有关、跟数据文件无关，所以评测脚本给每个 split 单独一个 `data.cache_dir`，否则会悄悄复用错的 split。
