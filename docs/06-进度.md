### 1. SFT 冒烟测试与分隔符 bug

- 第一次冒烟（`runs/1030-smoke-*`）两条标准都过了：lr=0 跑 20 步后 dev200 与 base 完全相同（9.0%，McNemar 0/0）；lr=1e-4 loss 下降。
- **但 val loss 20 步从 0.292 降到 0.098，太快**。排查过程（`code/scripts/sft_loss_breakdown.py`，结果 `runs/1030-smoke-sft-loss-breakdown.txt`）：
  1. 拆 loss：TinyGSM 预训练数据（不在 SFT 数据里）上的 loss 也降了约 5 倍——20 步不可能真的学到这么多，说明是格式问题；
  2. 排除 EMA（原始权重更差：10% 遮盖时答案词 CE 0.47 vs EMA 0.30）、排除校准（把 logits 放大只会更差）、对比 checkpoint 里保存的配置（模型和算法部分完全一致）；
  3. 只遮一个 token：base 在答案第 1 个位置（`def`）64 题全错（以 0.94 的概率预测成换行缩进），正文位置 64/64 全对——问题在题目与答案的交界；
  4. 交界处就是分隔符：预训练和评测用的是 yaml 单引号里的 `'\n'`，即**字面量反斜杠 + n**（token `[76, 94]`），`sft.py` 用的是真换行（`[198]`）。
- 修复后（`runs/1030-smoke2-*`）：base 的 val loss 0.116，20 步后 0.065；TinyGSM 上函数头各位置 64/64 全对、docstring top-1 100%、正文 top-1 99%（10% 遮盖）。lr=0 仍与 base 完全相同（9.0%，0/0），lr=1e-4 loss 0.094 → 0.074。**通过**。
- D1 的评测数字不受影响：评测一直用的是正确的分隔符。
- 教训（02「已更正的判断」）：lr=0 的冒烟标准查不出数据格式错误；训练分布要和 checkpoint 里实际保存的配置比，而不是和 yaml 默认值比。

### 3. dev 上的步数 × 温度扫描（新采样器，dev 1000）

| 步数 | T=1.0 | T=0.1 | 耗时 |
|---|---|---|---|
| 64 | 10.4% | 33.6% | 84 s |
| 128 | 14.3% | 36.2% | 148 s |
| 256 | 15.6% | 36.9% | 275 s |
| 512 | 17.8% | 38.8% | 532 s |
| 1024 | 17.5% | 38.1% | 1050 s |

相邻步数的配对 McNemar 检验：
- T=1：只有 64 → 128 显著（p=0.003）；128 → 256 p=0.39，256 → 512 p=0.14，512 → 1024 p=0.89；256 vs 1024 p=0.22。
- T=0.1：所有相邻对都不显著（p ≥ 0.13）；256 vs 1024 p=0.52。

读法：
- **步数**：128 步以后基本到平台，512 和 1024 没有区别。256 比 1024 低约 1–2pp，但不显著；耗时只有 1/4。
- **温度**：T=0.1 把准确率从约 17% 提到约 38%，翻了一倍多，和论文 Fig 3（T=0.1 约 33）方向一致，我们的数还更高。这意味着 **RL 的提升必须和"降温后的 base"比**（D16 的免费对照组），否则会把降温的效果算到 RL 头上。
- **错因**（256 步）：T=1 时 1000 题里 397 题代码执行报错或超时、447 题能跑但答案错；T=0.1 时报错降到 148 题、答案错 483 题。**降温主要修好的是"代码跑不起来"**，推理错误基本没少。这对 SFT / RL 的设计有用：base 在低温下的瓶颈是推理，不是格式。
- **dev 与 test 的差距**（04 §3.5）：1024 步、T=1 下 dev 17.5% vs test 15.9%，差 1.6pp。两个集合不同、不能配对，差值的标准误约 1.6pp，**不显著**。"dev 更简单"的担心目前证据不足，但 dev 仍然只用于相对比较。

### 实现说明（供下次接手）

- `fast_sampler.py` 三个开关：
  - `logits_mode=full`：和原版一样全量前向，再取出被选中的位置（逐字测试用）；`selected`：只在被选中的位置过输出层（正式用）。
  - `noise_mode=reference`：按原版的随机数消耗顺序生成全量 Gumbel 噪声，只用于逐字测试；`fast`：先抛硬币，只给选中位置生成噪声。
  - `skip_unchanged`：缓存隐状态，只对画布变了的序列重新前向（D07 的第二项优化，默认关）。
- 和原版的一处行为差异：某一步没有任何位置被揭开时，原版仍做一次前向，新版跳过。NFE 统计不同，生成分布不变。
- 逐字测试关掉了 `torch.compile`（`torch._dynamo.config.disable = True`）：原版 `sample_absorbing_posterior` 被 `torch.compile` 包着，编译后的 kernel 生成随机数的方式和 eager 不同，A800 上实测即使设 Inductor 的 `fallback_random=True` 也对不上（第一次测试 16 组全部"失败"就是这个原因，不是采样器的 bug）。算术相同，编译路径由层次 ② 的统计检验覆盖。
- AutoDL 把 `OMP_NUM_THREADS` 设成 0，libgomp 会报错，评测脚本里强制设成 8。
- 评测脚本：生成结果放在 `runs/<名称>/samples/`（不进 git），`metrics.json` 里存准确率、CI、耗时、显存峰值和每题对错字符串（以后做配对检验用）。
- 上游 `get_gsm8k_test_dataset` 的缓存目录只跟 tokenizer 有关、跟数据文件无关，所以评测脚本给每个 split 单独一个 `data.cache_dir`，否则会悄悄复用错的 split。
