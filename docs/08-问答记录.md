## Q6 步数怎么理解？为什么建议 256？

**答**：
- **步数的含义**：MDLM 一开始把题目后面的所有位置都设成 `[MASK]`，每一步做一次完整前向，揭开一部分位置。步数 N 就是把这些位置分 N 轮填完。
- **已核实**：调度是 `α_t = 1 − t`（`noise_schedules.py:60`）；每个还没揭开的位置每步被揭开的概率是 1/剩余步数，所以揭开在时间上是均匀的。
- **为什么步数少质量差**：同一步揭开的几个词是各自独立采的，它们之间的依赖会丢（比如运算符和后面要用的变量名搭配不上）。
- **为什么 256**：256 和 1024 在两个温度下都不显著（p=0.22 / 0.52），耗时是 1/4；评测要做约 40 次（**估计**），256 步共约 3 小时，1024 步共约 12 小时。
- **原回答里的错误**：当时说"256 步时大部分位置已经是一个一个填的"，Q7 更正。

## Q7 真有 450 个空位吗？空位少于步数，不就每步只揭开 1 个？

**答（已核实，dev 1000 实测长度）**：
- 画布固定 512，题目平均 63 个 token，所以平均要填 449 个位置（352–488）。但其中真正的答案平均只有 139 个 token（含 EOS），**其余约 310 个是 PAD**。模型不知道答案多长，靠预训练时学到的"预测 PAD"来控制长度（`train_on_pad=True`）。
- **不是每步固定揭开 1 个**：每个位置各自独立抛硬币，落在 N 步中的哪一步是均匀随机的，彼此不协调。就像把 200 个球随机扔进 256 个桶，有空桶，也有一桶装两三个的。
- **模拟**（真实长度，按调度规则）：

| 步数 | 每步平均揭开 | 空步占比 | 答案词中没和别的答案词同一步揭开 |
|---|---|---|---|
| 64 | 7.0 | 0% | 13% |
| 128 | 3.5 | 3% | 36% |
| 256 | 1.8 | 17% | 59% |
| 512 | 0.9 | 42% | 77% |
| 1024 | 0.44 | 64% | 87% |

- **更正**：Q6 说"256 步时大部分位置已经是一个一个填的"不准确。256 步时约 41% 的答案词和别的答案词同一步揭开。已记入 02「已更正的判断」。
- 引申：答案词单独揭开的比例从 59% 涨到 87%，准确率却只多 1–2pp 而且不显著，说明"同一步的词互相看不见"不是主要错误来源，主要错误在推理。

## Q8 空步不是浪费吗？原计划不是 128 步吗？128→256 不明显，256→512 更明显？

**答**：
- **空步**：原版采样器每步都做完整前向，空步确实浪费。新采样器有 `skip_unchanged`：这一步没有揭开位置的序列不参与前向，复用上次的隐状态。可以这样做是因为这个 MDLM 不以时间为条件（`time_conditioning: False`，**已核实**），画布不变输出就不变；它和默认路径 token 完全相同（**已核实**）。省多少还没实测，**估计** 512 步开 skip 后的耗时约是 256 步默认路径的 1.2 倍，1024 步约 1.4 倍。
- **128 步**：原计划里 128 是 **RL rollout** 的步数（D14 原文："rollout：64–128 步"）；评测主设置的候选一直是 256。不是从 128 改成了 256。
- **128→256 vs 256→512**：数字上你说得对（T=1：+1.3 vs +2.2pp；T=0.1：+0.7 vs +1.9pp），但这几个差都不显著，差值的标准误约 1.4pp。而且 1024 步在两个温度下都比 512 低，512 的峰值里应该有噪声。隔得远的比较更可靠：T=1 下 128 vs 512 显著（p=0.018），256 vs 512 不显著。
- **更正**：Q5 说"128 步以后基本到平台"说过头了。T=1 下 128 步明显不够，256 和 512 之间分不出来。
- **修改后的建议**：先实测 `skip_unchanged`。如果 512 步开 skip 后的耗时不超过 256 步的约 1.5 倍，主设置就用 512 步 + skip；否则用 256。
- **R30 实测与更正**：
  - 耗时（dev200，batch 200，只算采样）：512 + skip 是 256 默认路径的 **1.19 倍**，1024 + skip 是 1.47 倍，和上面的估计（1.2 / 1.4）基本一致（**已核实**）。按这条规则，D14 定为 512 + skip（R30）。
  - **原回答 → 更正**：上面说 skip "和默认路径 token 完全相同（已核实）"，说过头了。正确的说法是**同分布、但不逐位相同**。评测开了 TF32（`main.py:613`），cuBLAS 按矩阵大小选 kernel：只给部分行做前向时，子 batch 在 21–127 行（以及 1 行）会有舍入级差异，2–20 行和 128–200 行逐位相同（逐个大小扫过，**已核实**）。256 步时每步约 160 行前向，结果完全相同；512 / 1024 步时 dev200 上约 15% 的输出在某处分叉，逐题对错只差 1 / 4 题。原来的逐字测试没开 TF32、batch 又小，正好没碰到。缓存逻辑本身没错：一行只有被写入 token 时画布才会变，那时一定置 `dirty`（`fast_sampler.py:247`）。
  - 因此 SFT 扫描里 base 也在同协议（512 + skip）下重跑，配对比较都对它做。

## Q10 新采样器准确率高了一点，合理吗？切回有卡只要跑 15 分钟吗？

**答**：
- **合理，是随机波动**：
  1. 理论上分布相同；逐字测试在相同随机数下 token 完全相同（**已核实**）。
  2. 正常评测时，两边消耗随机数的顺序不同，同一个 seed 也会抽到不同的样本。同一个采样器只改 batch，准确率也会差 1–2pp（新版 batch 64 vs 200：17.0 vs 18.0；原版 batch 32 vs 64：4.0 vs 6.0）。
  3. 统计上，200 题里只有新版对的 24 题、只有原版对的 21 题，净差 3 题，标准误约 6.7 题，p=0.77。
  - **如实补充**：200 题只能检出约 7pp 以上的偏差，等价性主要靠层次 ① 证明。建议在 dev 1000 上补跑一次原版（约 13 分钟），和新版已有的结果按题配对，能检出约 3pp 的偏差。
- **不是只跑 15 分钟**：skip 测速约 15 分钟，加上层次 ② 补强约 13 分钟，共约半小时；D2 的 SFT 要一整天，而且要先定 D09、先写 SFT 代码。建议先在无卡模式写代码，写完再切有卡。

## Q11 怎么确保 DeepSeek 写的数据一定准确（就算用了过滤）？

**答**：**不能保证"一定"准确**，只能把错误率压低，并且如实测出剩下的错误率有多少。原因和对策：

1. **执行过滤只能验证"最终数字对"，验证不了"推理对"**。
   - 已知漏洞：
     - 答案凑对，例如代码里直接写 `result = 72`，或者中间步骤错了两次，正好抵消；
     - 用到题目里没有的数；
     - 代码和题目对不上（换了一道题的数字，答案却碰巧一样）。
   - 这类样本会教模型"凑答案"。SFT 之后 RL 用的奖励也只看最终答案，凑答案的习惯会被放大。
2. **gold 本身也可能错**。GSM8K train 的标注有少量错误，这是文献里提到过的问题，比例我没核实。执行结果和 gold 一致，只说明和人工标注一致。
3. **对策**（写进 SFT 数据管线）：
   - **硬过滤**（脚本）：
     - 能在沙箱里执行、和 gold 一致（容差同评测）；
     - 不允许直接 `return` 一个数字常量，或者把 gold 当作字面量写进代码；
     - 代码里出现的数字基本都要来自题目（允许 12、60、100 这类常见换算常数）；
     - 长度不超过预训练的 512 token 限制；
     - 格式与 TinyGSM 一致：`def simple_math_problem() -> ...:` + docstring + `return result`。
   - **独立验证**：用 GSM8K 自带的人写推理（`<<48/2=24>>` 这类中间结果）做交叉检查。DeepSeek 的代码里出现的中间值，应该能对上大部分 gold 中间结果。对不上的单独标记出来，不直接删，作为"可疑"样本做消融。
   - **抽样人工审查**：随机抽约 50 条，由我逐条读、对照题目判断推理是否正确，把审查结果存进仓库。这样能给出"过滤后错误率的上界估计"，例如 50 条里 0 条错，95% 置信上界约 6%。
   - **报告里如实写**：过滤后的数据只能说"执行答案与 gold 一致，抽查 X 条中 Y 条推理有误"，不能说"一定正确"。
4. **为什么这件事值得做**：D10 的消融（过滤 vs 不过滤）本来就是回答"数据对错有多大影响"。把"推理也对"的那部分再分出来，消融就能多一层：错误答案、凑对答案、推理正确，三档。

**实测结果（10-30 生成后补）**：详见 [data/sft/README.md](../data/sft/README.md)。
- 硬检查通过 6203 / 6473（95.8%）。
- 人工抽查 50 条通过的样本，推理有误 0 条，95% 上界约 6%。抽查 20 条可疑样本，也是 0 条有误：软检查精确率很低，只用来做消融。
- 被拒样本抽 24 条：19 条是 DeepSeek 错，2 条题目有歧义，**5 条是 GSM8K 标注错**（手算核对过）。所以"和 gold 一致"本身也不等于正确。

## Q13 有必要对全量做软检查吗？能用 DeepSeek 检查自己吗？

**答**：
- 规则式的软检查已经在全量上跑过了（几秒、零成本），但几乎抓不到真问题：抽查 20 条可疑样本，没有一条推理有误。你真正问的是要不要做全量的语义检查。
- **对 SFT 效果来说没必要**：50 条抽查 0 错，错误率上界约 6%，真实值估计约 1% 或更低，60 条左右的噪声对 SFT 的影响多半测不出来；D10 消融会直接回答"数据对错影响多大"。
- **DeepSeek 直接检查自己靠不住**：错误是相关的，它写错的地方往往正是它看不出来的地方；文献上，没有外部反馈时模型自我纠错效果很差（Huang et al. 2023, *Large Language Models Cannot Self-Correct Reasoning Yet*）；最关键的是不知道它的检出率。
- **如果要做，设计上必须**：不给 gold（否则退化成核对数字）；用思考模式（和生成时不同）；先在已知有错 / 已知正确的样本上**校准**检出率和误报率；它标出的由我人工复核。
- 建议：先做被剔除的 260 条（成本低，直接服务于 RL 题库）；全量可选。

## Q14 为什么要做被剔除的 260 条？

**答**：
- 不是为了 SFT（它们本来就不进 SFT），而是为了 **RL 题库的奖励是否正确**，以及**给全量检查做校准**。
- 260 条是"执行结果和 gold 对不上"的题，只可能是 DeepSeek 错、gold 错或题目有歧义。DeepSeek 准确率约 96%，gold 错了它多半会和 gold 对不上，所以**要找 gold 错的题，在这里找效率最高**。
- gold 错的题对 RL 有害：做对的样本拿 0 分，犯同样错的样本拿 1 分，GRPO 会强化这个错误（例 7472：该用除法的地方用了乘法，正是弱模型最容易犯的错）。它们还会污染 RFT 的难度估计。
- 在这里让 DeepSeek 判是可靠的：已经有外部信号指出分歧，而且同时给它两份推理（自己的和 GSM8K 的），判断"谁对"比凭空找错容易；判为 gold 错的我逐条手算复核。
- 它也是全量检查的前提：其中 DeepSeek 自己错的样本就是"已知有错"的校准集。
- 顺序：260 条裁决 → 校准 → 全量盲审。

### 1. 和采样器优化有关系吗 —— 没有

1. base 和 SFT 用同一个采样器、同一套参数，逐题配对比较，采样器的系统偏差会被配对差分抵消。

### 2. 为什么 T=1 劣化、T=0.1 持平

- SFT 把分布的熵压低了（数据是 6k 条风格极统一的代码，梯度把所有"别的写法"压下去）。T=0.1 近似取最大概率，压窄分布几乎无害；T=1 靠带温度的随机采样，分布被压窄后采样噪声更容易把模型推出正确轨迹。
- 诊断到的具体翻转例子：
  - `total=  = 36`：高温下的局部抖动；

## Q22 前面说评测比训练耗时长，是这样吗？为什么？（R34）

**答**：是。**已核实**（`runs/1030-pipeline-d2-sft.log`，截至 lr=1e-4 组）：训练 3 次共 10.7 分钟（每次约 3.6 分钟：5 epoch、475 步、batch 64），评测 30 次共 163 分钟（每次约 5.4 分钟：dev 1000、512 步 + skip）。每个 lr 训练 3.6 分钟、评测 54 分钟，约 15 倍。

**按单个样本算**：训练一条序列约 6.6 ms（200 秒 / 475 × 64 条，含前向 + 反向）；生成一个答案约 311 ms（311 秒 / 1000 题），约 47 倍。

**原因**：
1. 训练是一次前向 + 一次反向：随机遮掉一部分 token，所有被遮位置一次同时预测。
2. 生成要走 512 步，每步都对整条 512 长的画布做一次完整的双向前向（每步揭开几个位置，画布变了就要重算）。
3. 扩散模型用不了 KV cache：自回归模型生成时前面的 key/value 可以缓存，整段生成的总计算量约等于一次前向；MDLM 是双向注意力、画布每步都变，只能整条重算。
4. 实验设计：每个 lr 评测 10 次（5 epoch × 2 温度）× 1000 题。这是 D30 有意的取舍：训练便宜，所以每个 epoch 都评测，让扫描自己选 epoch。

采样器优化（D07：只在揭开位置算输出层、`skip_unchanged` 复用没变的行）已经把每步成本压低了，但"步数 × 完整前向"这个乘数去不掉。

**对 RL 的影响**：rollout 就是生成，所以 RL 的大头也在 rollout（03 §3：训练部分只占 rollout 的 20–30%）。因此 rollout 步数要比评测少（D14 原定 64–128 步，D4 调试时实测质量损失）；组大小 G 直接决定成本；全对 / 全错的组要在重算 log-prob 之前就丢掉（`rl/grpo.py` 的 `mixed_groups`）。

**答**：按现在的设置（512 步）直接落地，成本上不划算，但不是"完全不可行"。

- **实测吞吐**（A800，batch 200）：512 步 + skip 每题平均 0.31 s（dev 1000 约 311 s），dev T=0.1 38.6%；128 步 0.15 s，36.2%；64 步 0.08 s，33.6%（D1 扫描）。
- **与 AR 比**（**估计**，未实测）：单题延迟要 512 次串行前向，batch=1 每次几毫秒，约 2–4 s，和 AR 生成约 400 个 token 的串行步数同一量级；但 MDLM 每步重算全部 512 个位置，AR 有 KV cache 每步只算 1 个，所以每个答案的计算量约是 AR 的几百倍，吞吐差距估计一个数量级以上。
- **不是完全不可行**：
  1. 步数可调，上面就是速度–质量曲线；小模型步数少了质量掉得快，模型越强，每步能放心揭开的 token 越多。
  2. 扩散的潜在优势是并行：每步揭开很多 token 时步数可远小于长度。加速方向（**文献，未在本项目核实**）：近似 KV cache / 分块半自回归解码、按置信度并行解码、蒸馏到少步数（Duo 的离散一致性蒸馏、MDLM 的 SDTT）；Inception Labs Mercury、Gemini Diffusion 宣称每秒上千 token（厂商说法）。
  3. 本项目不以落地为目标，但报告可以加一节效率分析（D1 已有步数 × 准确率 × 耗时数据；D6 计划测 RL 后对步数的鲁棒性）。

### ② 5 轮够不够、loss 收敛了吗

**答**：loss 基本收敛了；更关键的是多训不会更好，反而更差（**已核实**）。

| lr | val loss（epoch 0→5） | T=0.1 准确率（各 epoch） | vs 同协议 base 38.6% |
|---|---|---|---|
| 1e-5 | 0.116 → 0.070 → 0.064 → 0.061 → 0.060 → 0.060 | 37.8 / 37.5 / 37.2 / 38.1 / 38.1 | e5 p=0.78，不显著 |
| 3e-5 | 0.116 → 0.060 → 0.056 → 0.054 → 0.053 → 0.053 | 37.8 / 38.5 / 36.9 / 36.6 / 36.4 | 后几轮在降 |
| 1e-4 | 0.116 → 0.053 → 0.051 → 0.050 → 0.050 → 0.049 | 35.8 / 32.8 / 32.2 / 32.4 / （跑中） | e2–e4 p ≤ 0.001，显著更差 |

- 最后一轮 val loss 只降 0.0001–0.0005，已平（部分因为 cosine 把 lr 降到 10%）；lr 越大 loss 越低，所以 1e-5 那组没到能达到的最低点；val loss 没有回升，没有过拟合迹象（val 比 train 低是因为训练时开着 dropout）。
- **准确率和 loss 反着走**：loss 拟合得越好，做题越差。val loss 衡量的是"模仿 DeepSeek 写法有多像"，不是"会不会做题"；拟合越用力，越往 6k 条数据的风格收窄、覆盖预训练学到的东西（遗忘），lr=1e-4 连 T=0.1 都掉了约 6pp。
- 结论：问题不在轮数，多训准确率大概率继续降。5 轮足以回答"SFT 有没有用"。
- 可以试的变体（混入 TinyGSM 原数据防遗忘、只训很少几步），但最温和的 1e-5 也只是持平，上限不高；建议不再投入 SFT，时间留给 RL。

## Q24 七点多跑完之后，如果能立刻开始 RL 就不关机；评估一下需要多少时间（R35）

**答**（估计，±50%，基于实测单价）：
- **开跑前要做的**：写 GRPO 训练循环（rollout → 丢全对全错组 → 抽轮 → old / new log-prob → 更新 → 定期 dev 评测、日志、checkpoint）约 45–60 分钟，可以在流水线跑的时候写；冒烟测试约 10 分钟；D3 检查点（rollout 准确率与评测脚本一致）约 3 分钟。19:30–20:00 可以开跑。
- **RL 本身**：实测单价——128 步生成一个答案约 0.13 秒（D1 扫描），一条序列前向 + 反向约 6.6 ms（SFT），每条保留的轨迹抽 8 轮约 70 ms。
  - 32 题 × G=8 = 256 条 rollout：每步约 45 秒；50 步加每 10 步 dev200 评测约 55 分钟。
  - 64 题 × G=8：每步约 90 秒。
  - D4 的 3 次 × 50 步约 3 小时，22:30–23:00 结束；300 步的正式跑（D5）约 4.5–8.5 小时，适合以后放在夜里。
- **关机的问题**：AutoDL 的 `/usr/bin/shutdown` 是直接杀掉 supervisord，容器立刻停止，不能取消。我停掉流水线外层脚本的操作被权限规则拦下，由你执行了 `kill 9585 9580`；当时正在跑的评测不受影响。之后用 `pipeline_d2_sft_resume.sh` 接着跑，关机条件改为"SHUTDOWN=1 且没有 `/root/autodl-tmp/KEEP_ALIVE` 文件"，跑的过程中还能改主意。

**定下**（R35）：今晚接着跑；D13 = base → RL 为主线；第一批 3 次 × 50 步扫学习率（D31）。
