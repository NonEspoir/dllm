## Q6 步数怎么理解？为什么建议 256？

**答**：
- **步数的含义**：MDLM 一开始把题目后面的所有位置都设成 `[MASK]`，每一步做一次完整前向，揭开一部分位置。步数 N 就是把这些位置分 N 轮填完。
- **已核实**：调度是 `α_t = 1 − t`（`noise_schedules.py:60`）；每个还没揭开的位置每步被揭开的概率是 1/剩余步数，所以揭开在时间上是均匀的。
- **为什么步数少质量差**：同一步揭开的几个词是各自独立采的，它们之间的依赖会丢（比如运算符和后面要用的变量名搭配不上）。
- **为什么 256**：256 和 1024 在两个温度下都不显著（p=0.22 / 0.52），耗时是 1/4；评测要做约 40 次（**估计**），256 步共约 3 小时，1024 步共约 12 小时。
- **原回答里的错误**：当时说"256 步时大部分位置已经是一个一个填的"，Q7 更正。

## Q7 真有 450 个空位吗？空位少于步数，不就每步只揭开 1 个？

**答（已核实，dev 1000 实测长度）**：
- 画布固定 512，题目平均 63 个 token，所以平均要填 449 个位置（352–488）。但其中真正的答案平均只有 139 个 token（含 EOS），**其余约 310 个是 PAD**。模型不知道答案多长，靠预训练时学到的"预测 PAD"来控制长度（`train_on_pad=True`）。
- **不是每步固定揭开 1 个**：每个位置各自独立抛硬币，落在 N 步中的哪一步是均匀随机的，彼此不协调。就像把 200 个球随机扔进 256 个桶，有空桶，也有一桶装两三个的。
- **模拟**（真实长度，按调度规则）：

| 步数 | 每步平均揭开 | 空步占比 | 答案词中没和别的答案词同一步揭开 |
|---|---|---|---|
| 64 | 7.0 | 0% | 13% |
| 128 | 3.5 | 3% | 36% |
| 256 | 1.8 | 17% | 59% |
| 512 | 0.9 | 42% | 77% |
| 1024 | 0.44 | 64% | 87% |

- **更正**：Q6 说"256 步时大部分位置已经是一个一个填的"不准确。256 步时约 41% 的答案词和别的答案词同一步揭开。已记入 02「已更正的判断」。
- 引申：答案词单独揭开的比例从 59% 涨到 87%，准确率却只多 1–2pp 而且不显著，说明"同一步的词互相看不见"不是主要错误来源，主要错误在推理。

## Q8 空步不是浪费吗？原计划不是 128 步吗？128→256 不明显，256→512 更明显？

**答**：
- **空步**：原版采样器每步都做完整前向，空步确实浪费。新采样器有 `skip_unchanged`：这一步没有揭开位置的序列不参与前向，复用上次的隐状态。可以这样做是因为这个 MDLM 不以时间为条件（`time_conditioning: False`，**已核实**），画布不变输出就不变；它和默认路径 token 完全相同（**已核实**）。省多少还没实测，**估计** 512 步开 skip 后的耗时约是 256 步默认路径的 1.2 倍，1024 步约 1.4 倍。
- **128 步**：原计划里 128 是 **RL rollout** 的步数（D14 原文："rollout：64–128 步"）；评测主设置的候选一直是 256。不是从 128 改成了 256。
- **128→256 vs 256→512**：数字上你说得对（T=1：+1.3 vs +2.2pp；T=0.1：+0.7 vs +1.9pp），但这几个差都不显著，差值的标准误约 1.4pp。而且 1024 步在两个温度下都比 512 低，512 的峰值里应该有噪声。隔得远的比较更可靠：T=1 下 128 vs 512 显著（p=0.018），256 vs 512 不显著。
- **更正**：Q5 说"128 步以后基本到平台"说过头了。T=1 下 128 步明显不够，256 和 512 之间分不出来。
- **修改后的建议**：先实测 `skip_unchanged`。如果 512 步开 skip 后的耗时不超过 256 步的约 1.5 倍，主设置就用 512 步 + skip；否则用 256。
- **R30 实测与更正**：
  - 耗时（dev200，batch 200，只算采样）：512 + skip 是 256 默认路径的 **1.19 倍**，1024 + skip 是 1.47 倍，和上面的估计（1.2 / 1.4）基本一致（**已核实**）。按这条规则，D14 定为 512 + skip（R30）。
  - **原回答 → 更正**：上面说 skip "和默认路径 token 完全相同（已核实）"，说过头了。正确的说法是**同分布、但不逐位相同**。评测开了 TF32（`main.py:613`），cuBLAS 按矩阵大小选 kernel：只给部分行做前向时，子 batch 在 21–127 行（以及 1 行）会有舍入级差异，2–20 行和 128–200 行逐位相同（逐个大小扫过，**已核实**）。256 步时每步约 160 行前向，结果完全相同；512 / 1024 步时 dev200 上约 15% 的输出在某处分叉，逐题对错只差 1 / 4 题。原来的逐字测试没开 TF32、batch 又小，正好没碰到。缓存逻辑本身没错：一行只有被写入 token 时画布才会变，那时一定置 `dirty`（`fast_sampler.py:247`）。
  - 因此 SFT 扫描里 base 也在同协议（512 + skip）下重跑，配对比较都对它做。

## Q10 新采样器准确率高了一点，合理吗？切回有卡只要跑 15 分钟吗？

**答**：
- **合理，是随机波动**：
  1. 理论上分布相同；逐字测试在相同随机数下 token 完全相同（**已核实**）。
  2. 正常评测时，两边消耗随机数的顺序不同，同一个 seed 也会抽到不同的样本。同一个采样器只改 batch，准确率也会差 1–2pp（新版 batch 64 vs 200：17.0 vs 18.0；原版 batch 32 vs 64：4.0 vs 6.0）。
  3. 统计上，200 题里只有新版对的 24 题、只有原版对的 21 题，净差 3 题，标准误约 6.7 题，p=0.77。
  - **如实补充**：200 题只能检出约 7pp 以上的偏差，等价性主要靠层次 ① 证明。建议在 dev 1000 上补跑一次原版（约 13 分钟），和新版已有的结果按题配对，能检出约 3pp 的偏差。
- **不是只跑 15 分钟**：skip 测速约 15 分钟，加上层次 ② 补强约 13 分钟，共约半小时；D2 的 SFT 要一整天，而且要先定 D09、先写 SFT 代码。建议先在无卡模式写代码，写完再切有卡。

## Q11 怎么确保 DeepSeek 写的数据一定准确（就算用了过滤）？

**答**：**不能保证"一定"准确**，只能把错误率压低，并且如实测出剩下的错误率有多少。原因和对策：

1. **执行过滤只能验证"最终数字对"，验证不了"推理对"**。
   - 已知漏洞：
     - 答案凑对，例如代码里直接写 `result = 72`，或者中间步骤错了两次，正好抵消；
     - 用到题目里没有的数；
     - 代码和题目对不上（换了一道题的数字，答案却碰巧一样）。
   - 这类样本会教模型"凑答案"。SFT 之后 RL 用的奖励也只看最终答案，凑答案的习惯会被放大。
2. **gold 本身也可能错**。GSM8K train 的标注有少量错误，这是文献里提到过的问题，比例我没核实。执行结果和 gold 一致，只说明和人工标注一致。
3. **对策**（写进 SFT 数据管线）：
   - **硬过滤**（脚本）：
     - 能在沙箱里执行、和 gold 一致（容差同评测）；
     - 不允许直接 `return` 一个数字常量，或者把 gold 当作字面量写进代码；
     - 代码里出现的数字基本都要来自题目（允许 12、60、100 这类常见换算常数）；
     - 长度不超过预训练的 512 token 限制；
     - 格式与 TinyGSM 一致：`def simple_math_problem() -> ...:` + docstring + `return result`。
   - **独立验证**：用 GSM8K 自带的人写推理（`<<48/2=24>>` 这类中间结果）做交叉检查。DeepSeek 的代码里出现的中间值，应该能对上大部分 gold 中间结果。对不上的单独标记出来，不直接删，作为"可疑"样本做消融。
   - **抽样人工审查**：随机抽约 50 条，由我逐条读、对照题目判断推理是否正确，把审查结果存进仓库。这样能给出"过滤后错误率的上界估计"，例如 50 条里 0 条错，95% 置信上界约 6%。
   - **报告里如实写**：过滤后的数据只能说"执行答案与 gold 一致，抽查 X 条中 Y 条推理有误"，不能说"一定正确"。
4. **为什么这件事值得做**：D10 的消融（过滤 vs 不过滤）本来就是回答"数据对错有多大影响"。把"推理也对"的那部分再分出来，消融就能多一层：错误答案、凑对答案、推理正确，三档。

**实测结果（10-30 生成后补）**：详见 [data/sft/README.md](../data/sft/README.md)。
- 硬检查通过 6203 / 6473（95.8%）。
- 人工抽查 50 条通过的样本，推理有误 0 条，95% 上界约 6%。抽查 20 条可疑样本，也是 0 条有误：软检查精确率很低，只用来做消融。
- 被拒样本抽 24 条：19 条是 DeepSeek 错，2 条题目有歧义，**5 条是 GSM8K 标注错**（手算核对过）。所以"和 gold 一致"本身也不等于正确。

## Q13 有必要对全量做软检查吗？能用 DeepSeek 检查自己吗？

**答**：
- 规则式的软检查已经在全量上跑过了（几秒、零成本），但几乎抓不到真问题：抽查 20 条可疑样本，没有一条推理有误。你真正问的是要不要做全量的语义检查。
- **对 SFT 效果来说没必要**：50 条抽查 0 错，错误率上界约 6%，真实值估计约 1% 或更低，60 条左右的噪声对 SFT 的影响多半测不出来；D10 消融会直接回答"数据对错影响多大"。
- **DeepSeek 直接检查自己靠不住**：错误是相关的，它写错的地方往往正是它看不出来的地方；文献上，没有外部反馈时模型自我纠错效果很差（Huang et al. 2023, *Large Language Models Cannot Self-Correct Reasoning Yet*）；最关键的是不知道它的检出率。
- **如果要做，设计上必须**：不给 gold（否则退化成核对数字）；用思考模式（和生成时不同）；先在已知有错 / 已知正确的样本上**校准**检出率和误报率；它标出的由我人工复核。
- 建议：先做被剔除的 260 条（成本低，直接服务于 RL 题库）；全量可选。

## Q14 为什么要做被剔除的 260 条？

**答**：
- 不是为了 SFT（它们本来就不进 SFT），而是为了 **RL 题库的奖励是否正确**，以及**给全量检查做校准**。
- 260 条是"执行结果和 gold 对不上"的题，只可能是 DeepSeek 错、gold 错或题目有歧义。DeepSeek 准确率约 96%，gold 错了它多半会和 gold 对不上，所以**要找 gold 错的题，在这里找效率最高**。
- gold 错的题对 RL 有害：做对的样本拿 0 分，犯同样错的样本拿 1 分，GRPO 会强化这个错误（例 7472：该用除法的地方用了乘法，正是弱模型最容易犯的错）。它们还会污染 RFT 的难度估计。
- 在这里让 DeepSeek 判是可靠的：已经有外部信号指出分歧，而且同时给它两份推理（自己的和 GSM8K 的），判断"谁对"比凭空找错容易；判为 gold 错的我逐条手算复核。
- 它也是全量检查的前提：其中 DeepSeek 自己错的样本就是"已知有错"的校准集。
- 顺序：260 条裁决 → 校准 → 全量盲审。

### 1. 和采样器优化有关系吗 —— 没有

- SFT 把分布的熵压低了（数据是 6k 条风格极统一的代码，梯度把所有"别的写法"压下去）。T=0.1 近似取最大概率，压窄分布几乎无害；T=1 靠带温度的随机采样，分布被压窄后采样噪声更容易把模型推出正确轨迹。
- 诊断到的具体翻转例子：

## Q22 前面说评测比训练耗时长，是这样吗？为什么？（R34）

**答**：是。**已核实**（`runs/1030-pipeline-d2-sft.log`，截至 lr=1e-4 组）：训练 3 次共 10.7 分钟（每次约 3.6 分钟：5 epoch、475 步、batch 64），评测 30 次共 163 分钟（每次约 5.4 分钟：dev 1000、512 步 + skip）。每个 lr 训练 3.6 分钟、评测 54 分钟，约 15 倍。

**按单个样本算**：训练一条序列约 6.6 ms（200 秒 / 475 × 64 条，含前向 + 反向）；生成一个答案约 311 ms（311 秒 / 1000 题），约 47 倍。

**原因**：
1. 训练是一次前向 + 一次反向：随机遮掉一部分 token，所有被遮位置一次同时预测。
2. 生成要走 512 步，每步都对整条 512 长的画布做一次完整的双向前向（每步揭开几个位置，画布变了就要重算）。
3. 扩散模型用不了 KV cache：自回归模型生成时前面的 key/value 可以缓存，整段生成的总计算量约等于一次前向；MDLM 是双向注意力、画布每步都变，只能整条重算。
4. 实验设计：每个 lr 评测 10 次（5 epoch × 2 温度）× 1000 题。这是 D30 有意的取舍：训练便宜，所以每个 epoch 都评测，让扫描自己选 epoch。

采样器优化（D07：只在揭开位置算输出层、`skip_unchanged` 复用没变的行）已经把每步成本压低了，但"步数 × 完整前向"这个乘数去不掉。

**对 RL 的影响**：rollout 就是生成，所以 RL 的大头也在 rollout（03 §3：训练部分只占 rollout 的 20–30%）。因此 rollout 步数要比评测少（D14 原定 64–128 步，D4 调试时实测质量损失）；组大小 G 直接决定成本；全对 / 全错的组要在重算 log-prob 之前就丢掉（`rl/grpo.py` 的 `mixed_groups`）。

**答**：按现在的设置（512 步）直接落地，成本上不划算，但不是"完全不可行"。

- **实测吞吐**（A800，batch 200）：512 步 + skip 每题平均 0.31 s（dev 1000 约 311 s），dev T=0.1 38.6%；128 步 0.15 s，36.2%；64 步 0.08 s，33.6%（D1 扫描）。
- **与 AR 比**（**估计**，未实测）：单题延迟要 512 次串行前向，batch=1 每次几毫秒，约 2–4 s，和 AR 生成约 400 个 token 的串行步数同一量级；但 MDLM 每步重算全部 512 个位置，AR 有 KV cache 每步只算 1 个，所以每个答案的计算量约是 AR 的几百倍，吞吐差距估计一个数量级以上。
- **不是完全不可行**：
  1. 步数可调，上面就是速度–质量曲线；小模型步数少了质量掉得快，模型越强，每步能放心揭开的 token 越多。
  2. 扩散的潜在优势是并行：每步揭开很多 token 时步数可远小于长度。加速方向（**文献，未在本项目核实**）：近似 KV cache / 分块半自回归解码、按置信度并行解码、蒸馏到少步数（Duo 的离散一致性蒸馏、MDLM 的 SDTT）；Inception Labs Mercury、Gemini Diffusion 宣称每秒上千 token（厂商说法）。
  3. 本项目不以落地为目标，但报告可以加一节效率分析（D1 已有步数 × 准确率 × 耗时数据；D6 计划测 RL 后对步数的鲁棒性）。

### ② 5 轮够不够、loss 收敛了吗

**答**：loss 基本收敛了；更关键的是多训不会更好，反而更差（**已核实**）。

| lr | val loss（epoch 0→5） | T=0.1 准确率（各 epoch） | vs 同协议 base 38.6% |
|---|---|---|---|
| 1e-5 | 0.116 → 0.070 → 0.064 → 0.061 → 0.060 → 0.060 | 37.8 / 37.5 / 37.2 / 38.1 / 38.1 | e5 p=0.78，不显著 |
| 3e-5 | 0.116 → 0.060 → 0.056 → 0.054 → 0.053 → 0.053 | 37.8 / 38.5 / 36.9 / 36.6 / 36.4 | 后几轮在降 |
| 1e-4 | 0.116 → 0.053 → 0.051 → 0.050 → 0.050 → 0.049 | 35.8 / 32.8 / 32.2 / 32.4 / （跑中） | e2–e4 p ≤ 0.001，显著更差 |

- 最后一轮 val loss 只降 0.0001–0.0005，已平（部分因为 cosine 把 lr 降到 10%）；lr 越大 loss 越低，所以 1e-5 那组没到能达到的最低点；val loss 没有回升，没有过拟合迹象（val 比 train 低是因为训练时开着 dropout）。
- **准确率和 loss 反着走**：loss 拟合得越好，做题越差。val loss 衡量的是"模仿 DeepSeek 写法有多像"，不是"会不会做题"；拟合越用力，越往 6k 条数据的风格收窄、覆盖预训练学到的东西（遗忘），lr=1e-4 连 T=0.1 都掉了约 6pp。
- 结论：问题不在轮数，多训准确率大概率继续降。5 轮足以回答"SFT 有没有用"。
- 可以试的变体（混入 TinyGSM 原数据防遗忘、只训很少几步），但最温和的 1e-5 也只是持平，上限不高；建议不再投入 SFT，时间留给 RL。

## Q25 现在 RL 的 reward 是怎么设置的？（R36）

**答**：奖励就是评测脚本自己的判分：**答对 1，否则 0**。没有格式分、部分分或长度惩罚（主线）。

- **怎么算**：`rl/rollout.py` 对每条答案调用上游的 `sandbox_gsm8k.evaluate_samples(response, gold, timeout_s=5)`，与评测完全相同：
  1. 提取代码：有 Markdown 代码块取代码块，否则从第一个 `def ` 开始；有语法错误就截到出错行之前；
  2. 受限环境执行：只开放少数内置函数，只能 import `math`，限时 5 秒；
  3. 调 `simple_math_problem()`：没有该函数、报错、超时都是 0；返回值转数字（接近整数的取整；字符串里找数字）；返回 None 就从打印内容里找数字；
  4. 与 GSM8K 答案 `####` 后的数字比较：整数必须相等，浮点允许 1e-3。
  - prompt（含字面量 `\n` 分隔符）和解码方式也与评测相同，所以训练时的奖励和评测时这道题算不算对是同一个判断。
- **变成学习信号**：同一题 8 个答案，(奖励 − 组均值) / 组标准差。8 个里对 2 个时：做对的 +1.73，做错的 −0.58。全对或全错的组优势为 0，提前丢掉（冒烟里每步保留约 40–56%）。
- **要如实说明的点**：
  1. 稀疏的二值信号："能跑但错"和"报错"都是 0。T=1 下 1000 题里 383 题是运行时错误。
  2. 判分器宽松（截掉出错后的代码、接受字符串和打印输出），但最后必须是正确的数字才有分，猜不中。
  3. 标准答案：GSM8K train，已去掉 161 道答案错 / 可疑 / 有歧义的题（`rl_exclude`），剩 6312 题。
  4. 优化的就是评测指标本身：没有代理指标偏差，但评测脚本若有漏洞模型会直接利用，D4 结果要抽查样本（`runs/<名称>/samples/`）。

## Q26 我感觉格式分还是需要的吧？可以开消融开关——你现在是要加到主线里还是加开关？（R36）

**答**：加开关，主线不动；今晚加两组消融，看结果再决定主线换不换。

- **数据支持你的直觉**（冒烟第 1 步的 256 条 rollout，128 步 T=1）：答对 19%，能跑但错 39%，运行时错误 39%，语法错 3%。32 题里 14 题（44%）组内全错，二值奖励下**整组没有学习信号**；而这 14 题每一题组内都同时有"能跑"和"报错"的答案，加格式分后都能产生"先写出能跑的代码"的信号。
- **关键的技术细节：格式分不能和组内标准差归一化一起用**。全错组里 4 条能跑（0.1）、4 条报错（0）：均值 0.05、标准差 0.05，能跑的优势 = +1.0、报错的 = −1.0，和"4 对 4 错"组里做对 / 做错的优势一样大。也就是说，除以组内标准差会把格式分放大到和正确性同样强，ε 设多小都没用；44% 的全错题里"能跑"被当成和"做对"一样重要，可能把模型推向"能跑但算错"的保守写法。所以加格式分时去掉组内标准差归一化（Dr. GRPO），ε 才真正控制权重：全错组里能跑的优势约 +0.05，有对有错组里做对的约 +0.5–0.9，格式信号约为正确性的十分之一。
- **定下**（R36）：格式分 ε=0.1，给"能跑且返回 / 打印出数字但答错"的答案；报错、语法错、超时、没有数字（几乎都是返回 None：判分器在语法错处截断，`return` 被截掉）都是 0。开关 `--format_reward 0.1`，配合 `--no_std`。
- **今晚 5 组**：原定 3 个 lr（二值 + std）+ lr=3e-6 二值去 std + lr=3e-6 格式分去 std。后两组只差格式分一个变量。
- **如实说明**：去掉 std 后优势变小（约 ±0.2–0.5 而不是 ±1），同一 lr 下实际步长更小。所以"3e-6 有 std"和"3e-6 无 std"的比较混了步长差异，不是纯粹的归一化对比；"有无格式分"那一对是干净的。
  - **原回答 → 更正（R37）**：这条说错了。优化器是 Adam，它按梯度自身的滑动尺度归一化，优势的整体大小不影响步长；实测 lr 3e-6 有 / 无 std 跑 50 步权重变化相同（0.014% vs 0.013%）。所以有 / 无 std 的对比也是干净的。"组内 std 会把格式分放大到与正确性同强"的论证不受影响（那是组与组之间的相对权重）。
- **一致性验证**：新写的 `rl/reward.py` 的 `grade()` 按上游判分逐步复刻并给出失败原因；在 4000 条已有评测输出上，"判为对"与上游完全一致（0 处不一致，`tests/test_rl_reward.py`）。

## Q27（补记）`gpu_mem_mib.txt` 里的 11109 这些数据是什么？（R34–R35 之间）

**答**：评测过程中每秒记录一次的**整张 GPU 显存占用**（MiB），是评测脚本的临时文件，不是结果数据。
- `code/scripts/eval_gsm8k.sh:44–46` 在评测开始时后台启动 `nvidia-smi --query-gpu=memory.used ... -lms 1000`；结束时（:72–75）停掉它、取最大值写进 `run_info.txt` 的 `peak_gpu_mem_mib`，然后删掉这个文件。看到它说明那次评测正在进行。
- 11109 MiB ≈ 10.8 GB（共 80 GB）：fp32 权重约 0.7 GB、CUDA 上下文约 0.5 GB、batch 200 × 512 的激活、`skip_unchanged` 缓存的隐状态（200 × 512 × 768 × 4 字节 ≈ 0.3 GB），以及 PyTorch 缓存分配器预留但没用的部分。用途：采样器第 ③ 层的显存对比（原版 47 GB → 新版 5–8 GB）、判断 batch 能否开大。
- **局限**：`nvidia-smi` 报的是整张卡，不是这一个进程。同一时间有别的程序用 GPU，峰值会被算进去。例：层次 ② 原版 dev 1000 记录 80859 MiB，单独跑 dev200 时是 47111 MiB，多出来的是我同时在跑的分隔符诊断。10-30 下午几个小测试与评测重叠，那几次的峰值也偏高。只影响显存记录，不影响准确率。以后要准确的单进程显存，改用 `torch.cuda.max_memory_allocated()`（`sft.py` 训练就是这么记的）。

## Q29 先讲清楚 3e-5 的情况和 1e-4 的情况，看哪个合适再决定（R37）

**答**：依据是自己测的"lr → 权重变化 → 行为变化"关系。

- **实测规律**：权重变化与 lr 成正比；与步数在"平方根到线性之间"（lr 1e-5：10 步 0.017%，50 步 0.045%，步数 ×5、变化 ×2.6，因为 RL 梯度噪声大，部分方向相互抵消）。
- **参照物**（SFT）：权重变化 0.12%（lr 1e-5 第 1 个 epoch）时风格明显改变、T=1 降 1.8pp；0.66%（lr 1e-4 第 1 个 epoch）时 T=0.1 降 2.8pp，第 2 个 epoch 起显著降约 6pp。
- **推算 300 步**（**估计**）：lr 3e-5 单次更新约 0.4%；lr 1e-4 单次更新约 1.3%（SFT 用 1e-4 训好几个 epoch 的量级，在 SFT 里那已经训坏了）；lr 3e-5 每批更新 4 次约 1%。
- **对比**：3e-5 较安全，风险是 300 步不够看出提升；1e-4 学得快（固定 8 题 30 步是我们见过最快的，但仍不明显），稳定性只验证了 30 步。RL 在模型自己的样本上提高对的、压低错的，不像 SFT 把分布拉向外部数据，所以通常能承受更大的步长；但 RL 有自己的失败方式（熵塌缩、不稳定），只能实测。
- **推荐的折中：lr 3e-5，每批更新 4 次**。rollout 占每步约 90% 时间，同一批多更新 3 次只多约 12 秒，学习量是单次的数倍；多次更新时 PPO clip 生效，每个 token 的概率比被限制在 [0.8, 1.28]，超出就停梯度，每批对策略的改动有上限。1e-4 单次更新时比率恒为 1，clip 不起作用，只能靠学习率控制。
- 另一道防线：每 25 步评测、最后按 dev 选最好的 checkpoint；实时记录动作 log-prob，快速趋向 0 就是熵塌缩信号。
- **定下**：lr 3e-5，每批更新 4 次（D32）。两臂各 300 步，每步约 50 秒，约 9.5 小时。

**怎么读**：方向对（在 T=1 训练，T=1 评测也在涨；T=0.1 暂未变，符合"先修好能跑的代码"的预期）。但只有一个评测点、+4.5pp 与 200 题约 3pp 的标准误同量级（p=0.078）；训练题上的上升可能含一点记忆成分（300 步约走 1.5 遍 6312 题的题库，题目有重复）。要等 300 步、12 个评测点、以及后 800 题的干净数字才能下结论。

### 二值臂 vs 格式分臂

两臂只差奖励，其余相同（base 起点、lr 3e-5、每批 4 次更新、不除组内 std、G=8、rollout 128 步 T=1、每步 32 题、300 步、同 seed 同题序）。

| | 二值臂 | 格式分臂 |
|---|---|---|
| 答对（执行结果 == gold） | 1 | 1 |
| 能跑且有数字但答错 | 0 | 0.1 |
| 报错 / 语法错 / 超时 / 没有数字 | 0 | 0 |
| 每步"有信号"的答案占比（实测） | 约 47% | 约 93% |
| 优点 | 奖励就是评测指标本身，没有歧义 | 把"跑不起来"和"算错"拆成两档，全错组也有信号 |
| 风险 | 信号稀疏，一半的失败拿同样的 0 分 | 模型可能学会"写能跑但算不对"的代码去拿 0.1（奖励被钻空子） |
| 看什么指标 | — | `cat_runtime` 应下降、"能跑但错"不应异常上涨 |

- **为什么都不除组内 std**：格式分和 std 归一化一起用时，0.1 会被放大到与"做对"同强（全错组 4 个 0.1、4 个 0，优势 ±1.0）。为了只差一个变量，二值臂也去掉（即 Dr. GRPO，同时去掉"按题目难度放大权重"的偏差）。
- **比较方法**：训练中两臂同题同步序，按步配对比较正确率（不是平均奖励）；收尾时每臂按事先定的规则选 checkpoint，再在 dev1000 上评测，报全集和后 800 题（后 800 题在选 checkpoint 时没用过）。

## Q32 看一下现在的结果，RL 有没有效果？现在是在基线上跑 RL，还是在 SFT 的 checkpoint 上跑？（R39，10-31 03:30）

**答**：
- **起点是基线**（D13 定的；`runs/1030-grpo-base-d5-binary/run_info.json` 的 `init_ckpt` 是 `mdlm.ckpt`）。
- **前约 150 步有效果，之后发散成乱码**（二值臂，跑到第 264 步时查看）。

**有效果的证据**：
- 训练正确率 0.145 → 0.21（第 50 步）→ 0.25（第 100–150 步）。题库 6312 题、每步 32 题不重复，前 197 步每步都是**新题**，所以这实际上是在新题上的准确率（rollout 128 步、T=1）。前 50 步与调试组同题对照：差值从 +0.003 升到 +0.07。
- dev200（与同协议 base 配对）：T=1 在第 75–100 步高出 6–8pp（第 100 步 29.5% vs 21.5%，p=0.033）；T=0.1 基本不动，只有第 150 步 47.5%（p=0.024），下一个点就回到 39%，很可能是噪声。
  - **原回答 → 更正（R39，dev1000 确认后）**：第 150 步 T=0.1 的提升不是噪声。dev1000 上 46.2% vs 38.6%，后 800 题 45.9% vs 38.5%，p < 0.001（见 Q33）。
- 如实说明：10 个评测点 × 2 个温度，单点 p≈0.03 不算强证据；可信的数字要等选中 checkpoint 在 dev 后 800 题上的结果。

**发散的现象**：

| 步数 | 被揭开 token 平均 log-prob | 平均输出长度 | 最后一次更新的 clip 比例 | 梯度范数 |
|---|---|---|---|---|
| 1–25 | −0.087 | 536 字符 | 0.9% | 0.03 |
| 101–125 | −0.065 | 515 | 1.2% | 0.03 |
| 151–175 | −0.18 | 531 | 2.9% | 0.04 |
| 226–250 | −1.3 | 830 | 16% | 0.26 |
| 251–264 | −1.8 | 947 | 22% | 0.31 |

dev200：第 175 步起掉到 base 以下，第 250 步 T=1 11%、T=0.1 27%（都显著更差）。第 250 步 256 条 rollout 里 210 条语法都不通，内容是乱码。权重相对 base：第 150 步 0.77%，第 250 步 2.8%。

**不是熵塌缩，是熵爆炸**：模型对自己采样的 token 越来越不确定，概率摊到大量无关词上；PAD 越写越少，输出变长、全是垃圾词。

**可能原因**（推测，未核实）：
1. 正负样本不对称：正确率约 0.2 时错的答案远多于对的；压低错误答案的 token，被压掉的概率摊到全词表的其他词上，熵升高；抬高正确答案的 token 只是让已经确定的词更确定。
2. 没有把模型拉回 base 的力量（D11 定的是"初期不加 KL，熵出问题再加"），也没有自动刹车；log-prob 从第 125 步就开始掉，流水线一直跑到底。
3. 扩散模型的自我强化：画布里一旦出现垃圾词，后面的生成以它们为条件，越来越多。
4. lr 3e-5 × 每批 4 次更新，累积步长偏大；clip 只限制单批内的变化，不限制跨批的累积漂移。

**定下（R39）**：停掉原流水线（二值臂剩下 36 步已是乱码，格式分臂用同样配置多半也会在 150 步左右崩）；格式分臂加**自动刹车**重跑，其余配置不变、最多 150 步；然后两臂按事先定的规则选 checkpoint（二值臂选中第 150 步）上 dev1000。

## Q33 崩掉的原因可能是学习率吗？（R39）

**答**：学习率是主要原因之一，但更准确的说法是：**学习率（更准确地说是有效步长 = lr × 每批更新次数 × 步数）决定多快走进不稳定区域，崩溃本身是一个自我加速的正反馈。**

- **和学习率有关的证据**：调试时 lr ≤ 1e-5、每批 1 次更新，50 步权重只动 0.045%，既没学到也没崩；正式跑 lr 3e-5 × 每批 4 次，150 步动 0.77%，学到了也崩了。lr 3e-5 × 4 次大致相当于单次更新 lr 约 1e-4，在 SFT 里是会训坏模型的量级。
- **说明不只是学习率**：lr 第 5 步后一直是常数 3e-5，但漂移在加速（前 150 步 0.77%，之后 100 步又 +2.1%），梯度范数 0.03 → 0.3、clip 比例 1% → 22%。若只是"每步太大"应该是匀速的；加速说明过了某个点后形成正反馈：画布出现垃圾词 → 后续生成以垃圾为条件 → 梯度更大更乱 → 更多垃圾。也没有把模型拉回去的力量（没有 KL、没有学习率衰减）。
- **另外两个可疑因素**（推测，未核实）：PAD 计入动作（D20）——输出长度 510 → 950 字符，PAD 越写越少，可能是错误答案里大量 PAD 被压低；负样本占多数——正确率约 0.2 时压低错误答案的 token，概率摊到全词表，熵升高。
- **怎么验证**（每个约 2.5 小时，白天定）：lr 1e-5 × 4 次更新（崩溃推迟还是消失）；lr 3e-5 + KL 到 base（能否保住速度又不崩）；`count_pad=False`（输出长度还涨不涨）。

**同时报告的结果**（二值臂第 150 步，按事先定的规则选中，dev1000 确认）：

| | base | RL 第 150 步 | 配对 McNemar |
|---|---|---|---|
| dev1000 T=1 | 18.0 | 28.5 | p < 0.001（+172 / −67） |
| dev 后 800 题 T=1（选 checkpoint 时没用过） | 17.1 | 29.4 | p < 0.001（+146 / −48） |
| dev1000 T=0.1 | 38.6 | 46.2 | p < 0.001（+171 / −95） |
| dev 后 800 题 T=0.1 | 38.5 | 45.9 | p < 0.001（+137 / −78） |

无选择偏差的后 800 题上 T=1 +12.3pp、T=0.1 +7.4pp；T=0.1 就是 D16 的"降温 base"免费对照，RL 也超过了它。

**同时报告的问题**：格式分臂第一次启动在第 1 步崩了——刹车的相对阈值代码里变量名 `first_logp` 与多次更新代码里的同名变量冲突。加相对阈值后只做了 import 检查和日志回放，没有用正式参数组合重新冒烟。已修复、用正式参数组合冒烟（`runs/1031-grpo-smoke-brake2`），由 `pipeline_d5c_grpo.sh` 重跑。

## Q34 前面说的 bug 是怎么回事？（R39）

**答**：同一个函数里两个变量重名。

## Q37 准确率是不是几乎没法提升到很高，比如 90 以上？（R42）

**答**：在现有设置下到不了 90%；现实的目标区间是 **50–55%**（dev，低温解码）。

### 三个硬约束

1. **模型容量 170M**：同一份 TinyGSM 数据上，同规模的 AR 模型也只到 54–63%（00 §1.4）。AR 是最有利的形式（一次一个词、看全部前文），也只到 60% 左右；扩散模型还要在同一轮里独立采样多个 token，更难。
2. **数据是合成的、带噪声**：TinyGSM 的 1185 万条代码是 GPT-3.5 生成、没有标准答案；模型学的是"GPT-3.5 怎么写小学生的代码"。SFT 的 6k 条质量高，但实测本身不涨分。
3. **一次生成，没有草稿和检查**：512 token 内一次写完，没有思维链、多次尝试、自我验算。能到 90%+ 的模型靠的都是这些。

### 我们自己数据里的上限

- **pass@8**（同题采 8 次、至少一次对的题占比，即"有没有能力做对"的上限）：二值臂第 1 步 56%、第 100 步 56%；格式分臂第 100 步 100%（那批题来自题库另一位置，更容易）。解码后的准确率只能接近它、不可能超过。
  - **原回答 → 更正（R43）**：
    - 格式分臂第 100 步的 100% 算错了，把格式分 0.1 也当成了"对"。按答对算是 62.5%（20/32）。
    - 两臂同 seed、同题序，第 100 步是同一批题，"来自题库另一位置"不对。
    - "不可能超过"也不严谨：这是 128 步、T=1 下 32 题的 pass@8，标准误约 9pp；pass@k 随 k 增大；它也不是另一种解码设置（512 步、T=0.1）准确率的上限。
    - 下面的 50–55% 只是粗估，不是推导出的上限；要量化，得在 dev 上用不同 seed 采样测 pass@k 曲线（D16）。见 09 §2.3。
- **解码方式的跨度**：同一模型 T=1 是 18%、T=0.1 是 38.6%，RL 后 T=0.1 是 45–46%。光选解码温度就在 18% 和 39% 之间拉了 20 多个点，说明能力本身不高，一直在争取"把已有能力更可靠地取出来"。

### 到 90% 需要什么

| 条件 | 现在 | 到 90% 大概需要 |
|---|---|---|
| 模型规模 | 170M | 7B 以上，通常还要配 CoT |
| 数据 | 1185 万条合成代码 | 真实、带验证答案的数据，或更强的教师 |
| 解码 | 一次生成 512 token | 思维链、多次采样 + 验证、工具调用与重试 |
| 训练 | SFT + GRPO | 更大规模 RL + 多轮拒绝采样迭代（D17 的退路就是多轮 RFT） |

前两条没有条件（预训练一次 $300 以上，7B 单卡跑不动）。

### 这次该期望什么

按 D16 的框架，报告要回答三个相对量：sft 有没有用（没有）；RL 有没有用（有：dev 后 800 题 T=1 17.1 → 29.4 / 31.9，T=0.1 38.5 → 45.9 / 45.1）；提升是否超过免费的解码技巧（超过，T=0.1 的 38.5% 就是免费的降温对照，RL 在它之上又多约 7 个点）。"不到 90%"不是失败；在 170M 的扩散模型上把 GSM8K 提到 45%（低温）/ 32%（T=1）并配全套消融，本身就有说服力；报告里把天花板讲清楚反而是加分项。

## Q40 tensorboard 里 train/action_logp、train/cat_no_fn 等好多图，哪个是 loss？为什么看不到收敛的图像？（R43）

**loss 是 `train/loss`，但它在 RL 里不反映收敛，这是正常的**：
- GRPO 的 loss 是一个"替代目标"，只有它的梯度有意义，数值本身没有。
- 优势 = 奖励 − 组内平均，同一组的优势加起来是 0。更新前比率又是 1，每条轨迹的动作数也几乎一样（PAD 计入），所以 loss ≈ Σ 优势 × 常数 ≈ 0，在 0 附近随机抖动。
- 这和 SFT 不一样：SFT 的 loss 是交叉熵，越低越好。

**为什么看不到"收敛曲线"**：
1. 每步换 32 道新题，单步的训练正确率主要由这批题难不难决定（D4 发现 5 组调试的曲线几乎重合）。要么看滑动平均，要么看固定的留出集。
2. 学习率是常数、没有衰减；我们靠"按 dev 选最好的 checkpoint"（早停），不是训到收敛。

**该看哪几张图**（`code/scripts/runs_to_tb.py` 新加了 `0_key/` 一组，排在最前面）：

| 图 | 含义 | 怎么读 |
|---|---|---|
| `0_key/dev200_T1.0`、`0_key/dev200_T0.1` | 每 25 步在留出的 dev200 上评测（与 `base-reference` 的水平线对比） | **最主要的学习曲线**；单点噪声约 ±3pp |
| `0_key/train_correct_ma25` | 训练 rollout 正确率的 25 步滑动平均 | 上升 = 在学；第 198 步以后是第二遍题库，含记忆 |
| `0_key/train_reward_ma25` | 奖励（答对 1 + 能跑但错 0.1）的滑动平均 | 同上 |
| `0_key/action_logp_ma25` | 被揭开 token 的平均 log-prob | 健康度：明显往下掉 = 发散前兆（二值臂第 150 步后就是这样） |
| `0_key/runtime_error_ma25` | 运行时错误占比 | 应下降 |

其余的 `train/*` 是原始逐步数据，查问题时用（如 `train/grad_norm` 看尖峰，`train/resp_chars` 看输出变长）。

## Q44 下一批任务的选项 2 / 3 / 4、定稿规则没太懂；为什么推荐的不是修好的 KL；为什么不推荐 SFT epoch 5（跑完不是更完整吗）；格式分、KL、二值分别有啥区别？（R43）

**选项 2 / 3 / 4 和定稿规则**：
- **2. 格式分臂跑满 300 步**：验证"只用格式分会不会崩"（Q42）。前 150 步顺带重复一次原格式分臂，可以看出同配置跑两次差多少。
- **3. 修好 KL 再跑**：给 k3 设上限、梯度异常时跳过这次更新，再看 KL 能不能防崩。
- **4. ELBO 对照**：只把 log π 的算法换成 d1 式近似，回答"精确 vs 近似"。要先写代码。
- **定稿规则**：D6 只拿一个 RL 模型上 test。规则要在看到更多结果之前定下，避免"挑樱桃"把数字抬高。

**为什么先跑格式分 300 步、而不是修好的 KL**：
1. **KL 实验需要对照**：要说"KL 防住了崩"，前提是"不加 KL 会崩"。格式分在 150 步以后会不会崩，现在不知道。如果先跑 KL、它没崩，又会回到今天的局面：分不清是 KL 的功劳，还是本来就不会崩（Q42）。格式分 300 步就是两个问题都需要的对照。
2. **结果决定下一步**：不崩，就不需要 KL，配置越简单越好；崩了，明天再跑修好的 KL，时间够（11-01 到 11-03）。
3. **不改代码、风险低**：KL 的修复要新写截断和跳过逻辑；Q34 的教训是，夜里跑刚改过的训练循环风险更高。
4. **附带的种子重复**：前 150 步能补上"只有一个 seed"的局限。

**为什么推荐 epoch 1、不推荐 epoch 5**：

"跑完"不等于"更好"。在 SFT 里多训几个 epoch，模型在 DeepSeek 写法上拟合得更好（val loss 更低），做题反而更差（Q23）。

| | T=1 | 与 base 配对 | T=0.1 | 与 base 配对 |
|---|---|---|---|---|
| base | 18.0 | — | 38.6 | — |
| SFT epoch 1 | 16.2 | p=0.095（不显著） | 37.8 | p=0.57 |
| SFT epoch 5 | 14.7 | p=0.007（显著更差） | 38.1 | p=0.78 |

- RL 用 T=1 采样，起点在 T=1 越准，组内有对有错的题越多，学习信号越强。epoch 1 在 T=1 下与 base 没有显著差别，epoch 5 显著更差。
- 按 D30 的规则（两温度平均最高），选出的也是 epoch 1（27.0，epoch 5 是 26.4）。
- 按 dev 挑最好的 epoch 是标准的早停做法，不比"最后一个 epoch"更不合规。
- 选 epoch 5 也说得通：它代表"完整的 SFT 配方"。代价是 RL 从一个更差的起点出发。

**格式分、KL、二值的区别**：三臂都是 GRPO、从 base 出发、lr 3e-5、每批更新 4 次、同样的题目顺序，只差奖励和正则。

| 臂 | 答对 | 能跑、出了数字但错 | 报错 / 语法错 / 超时 | 额外的正则 |
|---|---|---|---|---|
| 二值 | 1 | 0 | 0 | 无 |
| 格式分 | 1 | 0.1 | 0 | 无 |
| 格式分 + KL | 1 | 0.1 | 0 | KL：偏离起点越远，罚得越多（β=0.04） |

- **例子**：一组 8 个答案，2 对、3 能跑但错、3 报错。二值奖励是 [1, 1, 0, 0, 0, 0, 0, 0]；格式分是 [1, 1, 0.1, 0.1, 0.1, 0, 0, 0]。
- 如果 8 个全错，二值臂全是 0，整组没有学习信号。这样的组约占 44%。格式分臂里能跑的仍比报错的多 0.1，给出"至少写出能跑的代码"这个弱信号，所以有信号的答案从约 47% 升到约 93%。
- **结果**：三臂都比 base 显著好，彼此之间不显著。训练过程上，二值臂第 150 步后崩了；格式分臂截在 150 步；KL 轮 300 步没崩，但被第 14 步的尖峰混淆。
