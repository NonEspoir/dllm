# 开工决策详解：4090 的短板、D07、D08、D17

> 写于 2026-10-29。配合 [02-决策记录.md](02-决策记录.md) 阅读。文中耗时都是按规格推算的估计，误差约 ±50%，D1 实测校准。
> 已定的前提：用 4090；预算不设上限（D24），所以时间是唯一的硬约束。

## 1. "采样器改完后，4090 的短板基本消失"是什么意思

### 1.1 短板从哪来：原版采样器每一步做什么

以 batch 16 为例，每一步：

1. 模型前向，得到每个位置在整个词表上的分数：[16 条 × 512 位置 × 49152 词] ≈ **4 亿个数**。
2. 把这 4 亿个数转成 float64，一份就是 **3.2 GB**。
3. 对 4 亿个数全部做 exp、生成随机数、取 log、做除法、取 argmax，也就是给**每个位置**都采样一个词。
4. 最后只保留"仍是 mask、且这一步被选中揭开"的位置，其余结果全部丢弃。

问题在第 3 步：256 步时，每条序列每步平均只揭开约 1.8 个位置，16 条加起来不到 30 个。也就是说，4 亿次 float64 运算里，真正被用到的不到 0.01%。

这一步正好打中 4090 的两个短板：
- **FP64 慢**：4090 的 float64 算力只有 float32 的 1/64（约 1.3 TFLOPS）。A800 是 9.7 TFLOPS，快 7.5 倍。
- **显存小**：几份 3.2 GB 的 float64 张量同时存在，batch 16 就要占 8–10 GB。batch 32 在 24 GB 上已经很紧，batch 64 放不下。

### 1.2 改完之后

先决定哪些位置揭开，再**只在这些位置**算词表分数并采样。float64 的运算量和显存都缩小几百到上千倍，两个短板也就无关紧要了。

还有一个附带收益：输出层（768 × 49152）约占模型前向计算量的 28%，现在也只在这几十个位置上算，前向本身也快了。

| 4090，每一步（batch 16） | 原版 | 改后 |
|---|---|---|
| 模型前向 | 约 27 ms | 约 20 ms |
| float64 采样 | 约 25–55 ms（取决于 `torch.compile` 融合了多少） | <0.1 ms |
| float64 显存 | 8–10 GB | 几 MB |
| 能开的 batch | 16–32 | 128 以上 |
| 全量 test，256 步 | 约 18–29 分钟 | 约 5–7 分钟 |
| 全量 test，1024 步 | 约 1.2–2 小时 | 约 30 分钟 |
| 一个 RL 步的 rollout（128 条 × 128 步） | 约 70 秒（只能分 8 批跑） | 约 20 秒（一批跑完） |

### 1.3 为什么不用三张卡都测了（含一处更正）

我之前说"三张卡每次评测的花费差不多"，**不准确**。按规格重算：

| | 原版采样器 | 改后采样器 |
|---|---|---|
| 主要耗时 | 模型前向 + 大量 float64 运算 | 只剩 bf16 模型前向 |
| 速度（相对 4090） | 5090 约 1.5×，A800 约 2.5–3× | 5090 约 1.3–1.5×，A800 约 1.7–2× |
| 每单位计算的花费（4090 ¥2/h、5090 ¥3/h、A800 ¥6/h） | 三者接近，但 float64 开销的估计范围很宽 | 4090 ≈ 5090；**A800 贵约 1.5 倍** |

准确的说法是：
1. **测速原本是为了消除不确定性。** 原版采样器的 float64 开销估计范围太宽（25–55 ms），而各卡 FP64 性能差距又很大，不实测就排不出哪张卡划算。
2. **改完之后，剩下的是标准的 bf16 Transformer 前向。** 各卡在这类计算上的相对速度是已知量，不用测也能估。
3. **预算不设上限之后，几十块钱的差距不再重要。** 而三张卡各配一遍环境要多花 1.5–3 小时，这才是真正稀缺的资源。

所以直接用 4090：生态成熟，单价最低。如果之后 RL 阶段时间吃紧，就再租一张 4090 并行跑，不换卡。

## 2. D07：采样器怎么改

### 2.1 改什么

| 步骤 | 原版（`samplers.py:59` `sample_absorbing_posterior`） | 改后 |
|---|---|---|
| 1 | 模型对**所有位置**输出词表分数 | 模型只算到最后一层隐状态 |
| 2 | 对所有位置在 float64 下采一个词 | 先抛硬币：每个 mask 位置以 (α_s−α_t)/(1−α_t) 的概率被选中揭开 |
| 3 | 抛硬币决定哪些位置揭开 | 只在被选中的位置算词表分数：除以温度 → mask 词设为 −∞ → float64 log_softmax |
| 4 | 被揭开的位置填入采到的词，其余丢弃 | 只在这些位置做 float64 采样，填回画布 |

改后的版本会顺手记录两样东西：每个被揭开的词的 log-prob，以及每个位置是在第几步被揭开的。

### 2.2 为什么生成结果的分布完全不变

- 给定当前画布，原版里每个位置的结果是相互独立的：以概率 d 被揭开并填入一个从 p_θ 里采的词，否则保持 mask。
- 没被揭开的位置采到的词会被直接丢掉，对结果没有任何影响。
- 所以"先采再丢"和"只在要用的地方采"得到的联合分布完全相同。

改的只是计算顺序，不改概率模型。这和 D07 否决的"关掉 float64"不同：关掉 float64 会改变采样分布。

需要注意一点：**同一个 seed 下，两版的输出不会逐字相同**，因为随机数的消耗顺序变了。所以验证要分两步做（见 2.4）。

### 2.3 为什么值得改：它本身就是 RL 的 rollout 引擎

路线 B 的轨迹法需要知道：每个位置在第几步被揭开、揭开时填的词的 log-prob 是多少（[03 文档](03-RL算法与模型.md) §3）。改后的采样器在生成时就把这两样记下来了。

换句话说，这段代码到 D3 写 rollout 时无论如何都要写，D1 先写好，既能给评测提速，又能提前把 RL 最核心的组件验证掉。

### 2.4 怎么验证

| 层次 | 做法 | 通过标准 | 在哪跑 |
|---|---|---|---|
| ① 逐字等价 | 测试模式下，让两版用同一份随机数：同一组"是否揭开"的硬币，同一份 Gumbel 噪声在被选中位置上的取值 | 输出 token **完全相同** | 4090，batch 2，几步即可（10-30 改：不在 Mac 上跑） |
| ② 统计一致 | 在 dev 200 题上，两版各跑一次（256 步，T=1） | 准确率之差在配对检验下不显著 | 4090 |
| ③ 记录收益 | 同上，记录每步耗时、峰值显存 | — | 4090 |

层次 ① 的一个细节（10-30 补充）：测试模式下，新版也要先算全量 logits、再取出被选中的位置。如果只对选中位置做矩阵乘，矩阵形状不同，bf16 的舍入可能有微小差异，会导致极少数 token 不同，测试就判断不出是 bug 还是舍入。正式运行时才走"只算选中位置"的快路径，快路径另外用"logits 数值接近"来检查。

层次 ① 是关键：它把"分布等价"变成了可以逐字比较的确定性测试，能抓住索引错位、温度漏除、mask 词没屏蔽这类 bug。

### 2.5 代价、风险和可选的第二项优化

- **工作量**：实现约 2–3 小时，测试约 1–2 小时。
- **风险**：写错了会悄悄污染所有评测结果。由层次 ① 兜底；如果半天内验证不通过，就回退原版采样器（见 D17）。
- **第二项优化（可选，建议先不做）**：MDLM 的输出与时间无关，所以画布没变的序列不需要重新前向。
  - 1024 步时约 2/3 的序列每步都不变，可省约 2/3。
  - 256 步时只省约 20%，128 步时基本没收益。
  - 只有 1024 步的复现会用到，跑一两次而已，不值得增加复杂度。

### 2.6 选项

| 选项 | 内容 | 建议 |
|---|---|---|
| A | 改（第一项优化）+ 三层验证 | **推荐** |
| B | 不改，用原版 | 评测慢 3–4 倍，RL rollout 要分批跑；D3 写 rollout 时还得另写一套 |
| C | 关掉 float64 提速 | 否决：会改变采样分布（Zheng et al. 2409.02908） |

## 3. D08：数据怎么分

### 3.1 三份数据

| 用途 | 来源 | 规模 | 能做什么 |
|---|---|---|---|
| 训练 | GSM8K train 去掉 dev | 6473 或 6973 | SFT 数据、RFT 采样、RL 题目 |
| dev | 从 GSM8K train 随机留出 | 1000 或 500 | 调参、选 checkpoint、测速、选评测步数 |
| test | GSM8K test | 1319 | 只用两次，见 3.3 |

GSM8K train 要从 HF 的 `openai/gsm8k` 下载（用 hf-mirror）；仓库里自带的只有 test。

### 3.2 dev 取多大

在准确率约 20% 时，95% 置信区间的半宽：

| dev 大小 | 置信区间半宽 | 训练集剩多少 |
|---|---|---|
| 200 | ±5.5pp | 7273 |
| 500 | ±3.5pp | 6973 |
| 1000 | ±2.5pp | 6473 |

配对比较（两个模型做同一批题）比上表更灵敏，但量级相同。

**推荐 1000**（原计划是 500，这里改了建议）：
- 采样器改完后，dev 1000 题跑 256 步只要 4–5 分钟，大 dev 不再昂贵。
- RL 和 SFT 阶段的结论要分辨 2–3pp 的差距，dev 500 不够用。
- 训练集少 7% 影响很小：RL 跑 300 步 × 每步 16 题 = 4800 题次，6473 题够用，不会重复。

### 3.3 test 只允许两种用法

1. **D1 复现**：按论文的固定设置（1024 步、T=1），对原始 checkpoint 跑一次。这是校准评测流程，不做任何选择。
2. **最终评测**：所有定稿的模型各跑一次。

除此之外的一切选择，包括步数、温度、学习率、用哪个 checkpoint，都只看 dev。

### 3.4 怎么切

- 固定 seed 随机抽 dev，把题目编号存成 `data/splits/gsm8k_dev_ids.json`，提交进 git。之后所有代码都从这个文件读，不再重新切。
- D1 测速用的"dev 200"就是 dev 的前 200 题，也是固定的。

### 3.5 一个隐患：dev 可能偏简单

TinyGSM 论文写明，它的题目是**以 GSM8K train 的题为种子**，让 GPT-3.5 生成"类似的变体"。dev 是从 GSM8K train 里切的，所以预训练时模型很可能见过 dev 题的变体，而 test 题没有这种待遇。

后果是：dev 上的准确率可能比 test 高，dev 只适合做**相对比较**（A 模型比 B 模型好多少），不适合当绝对水平。

处理办法：D1 用同一个固定设置，分别测原始模型在 dev 和 test 上的准确率，把差距记录下来，写进报告。这个现象本身也是面试时能讲的一个细节。

### 3.6 选项

| 选项 | 建议 |
|---|---|
| dev 1000 / train 6473 | **推荐** |
| dev 500 / train 6973 | 也可以，置信区间宽一些 |
| 另外再做 TinyGSM ↔ test 的 13-gram 重叠检查 | 推荐。TinyGSM 论文附录 A.2 做过同样的检查，可以对照 |

## 4. D17：止损点

止损点的作用：提前约定"出现什么情况就停下来换做法"，避免在一个坑里耗掉整周。

### 4.1 D1：复现不在 18±3%，就停下来修评测

- **检查什么**：用**原版采样器**（先排除我们改动的影响），1024 步、T=1，跑全量 test，看准确率是否落在 15–21%。
- **为什么阈值是 ±3**：单次运行在 18% 附近的标准误约 1.06pp。我们的结果和论文的结果是两次独立运行，两者之差的标准误约 1.5pp，95% 范围约 ±2.9pp。所以超出 ±3，就不太可能只是随机波动。
- **触发后查什么**（按可能性排序）：
  1. 步数没设对：官方采样脚本默认 `STEPS=32`，论文的 18.0 是 1024 步；
  2. 没用 EMA 权重：已核实默认会用（`main.py` 里的 `_eval_mode` 会把 EMA 权重拷进模型），除非设了 `disable_ema`；
  3. tokenizer、分隔符、长度截断和训练时不一致；
  4. 代码抽取或判分逻辑有问题。
- **耗时**：原版采样器在 4090 上跑这一次约 1.2–2 小时。放在后台跑，同时写新采样器，不浪费时间。

### 4.2 新增：D1–D2，采样器验证半天内不通过，就回退原版

- 对应 D07 的层次 ①②。
- 回退的代价：评测慢 3–4 倍，可以接受；RL rollout 的记录功能另写一个"慢但简单"的版本。

### 4.3 D3：rollout 打分要和评测脚本一致

- **检查什么**，分两项：
  1. 同一批生成文本，分别交给 RL 的奖励函数（多进程版）和官方评测函数打分，结果必须 **100% 一致**；
  2. rollout 代码在 dev 上生成的准确率，与评测脚本在相同设置下的准确率，差距在配对检验下不显著。
- **为什么**：如果奖励函数和评测口径不一致（比如多进程里超时处理不同、代码抽取不同），RL 优化的就是一个错误的目标，训得越好，评测反而可能越差。
- **触发后**：先修好再开始训练。

### 4.4 D5 晚上：RL 在 dev 上没有提升，就改用多轮 RFT

- **"没有提升"的定义**：最好的 RL checkpoint 与 SFT 模型在 dev 上比，配对检验不显著，或者提升不足 2pp。
- **D4 的早期信号**：训练奖励在上升但 dev 不涨，说明过拟合了训练题；训练奖励都不涨，多半是 bug 或学习率问题。
- **退路：多轮 RFT（expert iteration）**：每轮在训练题上每题采 8 个答案，留下做对的，用标准 MDLM loss 做 SFT。重复 2–3 轮，每轮约 2 卡时。
  - 它是 RL 最简单的形式：只奖励做对的，不压低做错的。
  - 不依赖轨迹 log-prob 这套机制，风险低，保证有东西可交付。
- **同时要做**：把 GRPO 失败的现象和分析写进报告。题目明确说了，没做出来的部分要说明试了什么、卡在哪里。

### 4.5 选项

| 止损点 | 推荐阈值 | 可调整的方向 |
|---|---|---|
| D1 复现 | 18±3% | 收紧到 ±2 会增加误报，不建议 |
| 采样器验证 | 半天 | 可以放宽到一天，但会挤占 D2 |
| D3 打分一致 | 100% 一致 + 准确率差距不显著 | 不建议放宽 |
| D5 RL | 配对检验不显著或 <2pp → 多轮 RFT | 可以把截止推到 D6 中午，代价是分析时间被压缩 |
