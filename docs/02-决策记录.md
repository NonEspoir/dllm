## 三、逐条说明（按编号，供查阅）

### D01 做哪个方向 —— 方向一（已定，10-29 确认）

- **推荐**：方向一（基于预训练 checkpoint 做 SFT + RL）。
- **理由**：
  - 方向二按官方配置完整训一次 MDLM 要 182.7 H100·小时。¥100 只够每个方案训到官方的约 2–5%，GSM8K 分数会被噪声淹没，做不出题目要求的 benchmark 对比（分析 §1.1、§1.1.1）。
  - 方向一的提升空间明确：MDLM 仅降温就能从 18% 涨到约 33%（分析 §1.2）。
  - 标准工作量在 ¥100 内（分析 §6）。
- **否决的备选**：方向二。如果自己垫钱，每个方案训到官方的 20% 约需 ¥440–585，且至少 4 卡并行。
- **何时重新评估**：除非预算能放大到几百元以上，否则不再讨论。

### D02 主模型 —— s-flm 仓库里的 MDLM checkpoint（已定，10-29）

> 命名澄清："s-flm" 是 HF 仓库 / 论文的名字，仓库里放了 AR、MDLM、Duo、FLM、CANDI、S-FLM 共 6 类模型的 checkpoint。D02 选的是其中的 **MDLM**（`tinygsm/mdlm.ckpt`），**不是** S-FLM 模型本身。

**第一层：为什么用这个仓库的 checkpoint，而不是外部模型**

- 预训练数据就是 TinyGSM，契合题目"围绕 TinyGSM"。
- 论文给了每个模型的 GSM8K 分数，可以用来校准复现。
- 训练、采样、评测代码统一。
- 170M 规模，¥100 内能做 RL。
- 外部候选的问题见 D04。

**第二层：为什么在仓库内选 MDLM**（RL 的三个硬条件，逐个筛）

| 条件 | MDLM | Duo | S-FLM | FLM / CANDI |
|---|---|---|---|---|
| ① 起点准确率（T=1） | 18.0 | 17.2 | 12.4 | 0.3 / 0.2 |
| ① GRPO 每组 8 个里"有对有错"的概率（按每题准确率都等于均值粗算） | 0.80 | 0.78 | 0.65 | 0.02 |
| ② 采样策略的 log π 怎么算 | 每轮只有新揭开的位置依赖 θ，共约 L 个项，精确 | 每轮**每个位置**的转移概率都依赖 θ（`keep_xt_prob` 用到 p_θ(x_t)），共 K×L 个项；可算但方差大、计算贵 | 默认 exact 模式是确定性 ODE，没有随机动作，策略梯度用不了；sample 模式下有 K×L 个离散动作，还要穿过连续状态做信用分配 | — |
| ③ 可借鉴的 RL 文献 | 最多（d1、wd1、SPG、coupled-GRPO、TraceRL 都基于 masked diffusion） | 很少 | 基本没有（连续流 RL 要参考图像领域的 Flow-GRPO 一类） | — |
| 降温的提升空间 | 18 → ≈33 | 17.2 → ≈36 | 12.4 → ≈18 | <0.5 |

- **FLM / CANDI**：被条件 ① 直接淘汰。准确率约 0.2–0.3%，98% 的组全错，RL 几乎拿不到学习信号。
- **S-FLM**：被条件 ② 淘汰。默认采样是确定性的，要做 RL 得先改造采样器，风险太大，所以只写可行性分析。
- **AR**：题目禁止。
- **MDLM vs Duo 是真正的二选一**：
  - 分数差 0.8pp，在 ±2.1pp 的置信区间内，可以算打平；低温下 Duo 还更高（36 vs 33）。
  - 所以选 MDLM 的决定性理由不是分数，而是条件 ② 和 ③：log π 只有约 L 项且精确，文献和工具最多。
  - 另外，D07 的采样器优化只适用于 MDLM。
- **Duo 的独特优势**：已生成的 token 还能被改写，有"自我纠错"能力，RL 也许能利用这一点。这正是把 Duo 列为加分项（D03）的原因：主线跑通后迁移过去，比较两类扩散在 RL 下的表现。
- **代码依据**：`samplers.py:59`（MDLM）、`samplers.py:112`（Duo）、`samplers.py:556`（S-FLM velocity）。

### D04 是否换"数据更干净"的 checkpoint —— 不换（待你确认）

- **理由**：
  - 同一份 TinyGSM 数据上，AR 170M 能做到 54–63%。说明数据噪声不是 MDLM 只有 18% 的主因（分析 §1.4）。
  - 候选 checkpoint 各有硬伤：
    - SMDM-GSM8K：已经做过 SFT；成本约 4 倍；58.5 分无法归因到数据质量。

    - Dream 等：由 AR 权重转来，处于题目规则的灰区。
- **替代方案**：用 D10 的 SFT 消融，在方向一内部受控地回答"数据对错有多大影响"。

### D07 采样器改造（已定，10-30）

- **改法（10-30 补充）**：不改原文件里的已有代码，而是**新增**一个采样器类（暂名 `FastAncestralSampler`）和对应的配置文件，用配置切换新旧版本。原版保留，用于 D1 复现、等价性验证和回退。

### D12 RL 的 log-prob 计算 —— 主线轨迹法（待你确认）

### D14 步数与温度（已定，R30：512 步 + `skip_unchanged`，T ∈ {1, 0.1}）

> **R30 定下**：你同意按 08 Q8 的规则自动定，规则是"512 步开 skip 的耗时 ≤ 256 步默认路径的约 1.5 倍就用 512 + skip，否则 256"。
>
> **实测**（`runs/1030-D2-checks-summary.md`，dev200，batch 200，T=1，只算采样时间）：
>
> | 步数 | 默认路径 | skip | skip 相对 256 默认 |
> |---|---|---|---|
> | 256 | 53 s | 44 s | 0.83 |
> | 512 | 104 s | 63 s | **1.19** |
> | 1024 | 208 s | 78 s | 1.47 |
>
> 1.19 ≤ 1.5，所以主设置用 **512 步 + skip**。Q8 估的是 1.2 倍（512）和 1.4 倍（1024），估计基本准。
>
> **为什么推荐这条规则、为什么最后是 512**：
> 1. **准确率**：dev 1000 上 512 比 256 在两个温度下都高（T=1：17.8 vs 15.6；T=0.1：38.8 vs 36.9），单看都不显著（p=0.14 等），但方向一致；1024 没有比 512 更好（17.5 / 38.1）。
> 2. **机制**：步数越多，同一步里一起揭开的答案词越少，"同一步揭开的词之间互相独立"这个近似带来的误差越小。dev 上模拟，只和自己单独揭开的答案词，256 步是 59%，512 步是 77%（见「已更正的判断」10-30 那条）。
> 3. **代价**：开 skip 后 512 只比 256 默认路径慢约 19%，dev 1000 一次评测从约 4.6 分钟变成约 5.5 分钟；1024 + skip 又贵约 25%，但没有更好，所以不用。
> 4. **留余量**：SFT / RL 后的模型对步数的敏感度可能不同，主设置用一个已在平台上的步数更稳。
> 5. 规则是在看到测速结果**之前**定的（Q8），避免看结果再挑。
>
> **注意（R30 实测，已更正 Q8 的说法）**：skip 和默认路径**同分布、但不逐位相同**。评测开了 TF32（`main.py:613`），cuBLAS 按矩阵大小选 kernel，子 batch 在 21–127 行（以及 1 行）时隐状态与整批有舍入级差异，2–20 行和 128–200 行逐位相同。256 步时每步约 160 行前向，结果完全相同；512 / 1024 步时约 110 / 66 行，dev200 上分别有 29 / 28 条输出在某处分叉，逐题对错只差 1 / 4 题。所以 SFT 扫描另跑了**同协议（512 + skip）的 base**，所有配对比较都对它做。
>
> 以下是 R30 之前的记录。

> **D1 实测后的建议（10-30，R30 前）**：

> **D1 实测**（06「D1 结果分析」§3）：dev 1000 上 128 步以后基本到平台；256 vs 1024 在 T=1 和 T=0.1 下都不显著（p=0.22、0.52），256 比 1024 低约 1–2pp，耗时 1/4（dev 4.6 分钟，test 约 6 分钟）。T=0.1 比 T=1 高约 21pp。
>
> **建议**：评测主设置 **256 步，T ∈ {1.0, 0.1} 两个温度都报**；定稿模型在 test 上另跑 1024 步、T=1 对齐论文。理由：256 已在平台附近，而开发期间要反复评测，省下的时间更值钱；RL 后模型对步数的敏感度可能改变，D6 的步数鲁棒性分析会单独测。
> 备选：主设置用 512 步（两个温度下都是最高值，但同样不显著），每次评测时间翻倍。
>

- **方案对比**：

  | 方案 | 做法 | 优点 | 缺点 |
  |---|---|---|---|
  | A. 本地 Claude + SSH（推荐） | Claude 在你的 Mac 上运行，通过 `ssh` / `rsync` 在服务器上执行命令、同步代码、查看日志 | 不用解决服务器的网络问题；本地记忆和文档都在；服务器关机不影响对话 | Mac 要保持联网；每条服务器命令前面要多一层 ssh |
  | B. 服务器上装 Claude Code | 在 AutoDL 实例里安装、登录、直接运行 | 命令直接在服务器上执行 | 要先解决网络问题；本地记忆不会同步过去；实例关机后对话中断 |

- **两种方案都需要**：仓库根目录的 `CLAUDE.md`（每次启动自动读入项目规则）和 [06-进度.md](06-进度.md)（交接当前状态）。这两个文件已按两种方案都能用的方式写好。

### D29 SFT 训练怎么接上游代码（实现时定，R27，我按默认做）

- **做法**：`code/scripts/sft.py` 用一个普通的 PyTorch 训练循环，**直接调用上游的 `MDLM._loss`**（与预训练相同的 NELBO），数据格式与预训练一致（`[BOS] 题目 SEP 代码 [EOS] [PAD]*`，`train_on_prompt=False`、`train_on_pad=True`）。不改上游任何文件。
- **R30 更正**：原来写"逐 token 对过"，但分隔符错了。上游 yaml 写的是 `separator: '\n'`（单引号，YAML 不转义），所以 SEP 是**字面量反斜杠 + n 两个字符**（token `[76, 94]`），预训练（checkpoint 里保存的配置）和 GSM8K 评测都是这样；`sft.py` 原来用的是真换行（token `[198]`）。已修复，并加断言要求 SEP 与 checkpoint 保存的配置一致。发现过程见「已更正的判断」和 06。
- **为什么不用上游的 `mode=train training.finetune_path=...`**（读代码和 checkpoint 核实）：
  1. `load_from_checkpoint` 恢复的是**训练权重**，但所有评测（包括我们测的 base）用的是 **EMA 权重**。发布的 checkpoint 里两者相对 L2 差约 10%（mmap 加载实测）。SFT 会从一个没测过的模型出发。
  2. 恢复的 EMA 衰减是 0.9999、`num_updates`=250k。几百步 SFT 后，被评测的 EMA 权重只会移动百分之几，等于 SFT 几乎没生效。
  3. Lightning 还会恢复预训练的 dataloader 进度和 2500 步 warmup。
- **因此**：从 EMA 权重出发，SFT 期间不用 EMA；保存的 checkpoint 让 `state_dict` 和 `ema.shadow_params` 指向同一组张量，评测脚本可以直接加载。
- **冒烟测试**（`code/scripts/smoke_sft.sh`）：lr=0 跑 20 步，dev200 准确率必须和 base 在同一 seed 下完全一样（验证"从 EMA 出发 + 保存格式"没错）；lr=1e-4 跑 20 步，loss 必须下降。
- **超参默认值**（需要学习率扫描定）：AdamW，weight decay 0、梯度裁剪 1.0（与上游相同）；batch 64；5 epoch；5% warmup + cosine 降到 10%。理由见 D30。

### D30 SFT 扫描设置；D10 消融用哪个学习率（已定，R30）

**扫描设置**（`code/scripts/pipeline_d2_sft.sh`）和理由：

| 项 | 取值 | 理由 |
|---|---|---|
| 数据 | `sft_v1b` 6232 条，留 2%（125 条）算 val loss | R29 定 v1b 为主数据；val loss 用来看过拟合，不用来选模型 |
| 学习率 | {1e-5, 3e-5, 1e-4} | 预训练是 3e-4 常数学习率（checkpoint 配置核实）。微调一般取预训练峰值的几十分之一到几分之一，这三个点是 1/30、1/10、1/3，按约 3 倍等比覆盖一个数量级。冒烟测试里 1e-4 稳定（梯度范数 0.18–0.29，低于裁剪阈值 1.0），所以上限不用更保守 |
| epoch | 5，**每个 epoch 存 checkpoint 并评测** | 数据只有约 6k 条，一个 epoch 只有 95 步，需要多轮；每轮都评测，等于让扫描自己选 epoch（早停），不用事先猜。训练很便宜（每个 lr 约 3 分钟），开销几乎全在评测 |
| batch | 64 | 与预训练每卡 batch 相同。预训练全局 batch 是 512，但 6k 条数据用 512 一个 epoch 只有 12 步，更新次数太少；64 时每 epoch 95 步。显存峰值约 35 GB |
| 学习率形状 | 5% warmup + cosine 降到峰值的 10% | 优化器状态是新建的（D29 不恢复预训练的 Adam 状态），先 warmup 避免前几步更新过猛；cosine 让后几个 epoch 步子变小、结果更稳 |
| weight decay / 梯度裁剪 / dropout | 0 / 1.0 / 0.1 | 都与预训练相同，少一个变量 |
| 评测 | dev 1000，512 步 + skip（D14），T ∈ {1, 0.1}，batch 200，seed 1 | 与 base 同协议，按题配对做 McNemar；base 也在同协议下重跑了一遍（见 D14 的注意） |

**D10 消融用哪个 lr**：消融只在一个 lr 上训 `unfiltered`，为了能无人值守跑完，选法要事先定死。

| 选项 | 说明 |
|---|---|
| **两温度平均（推荐，你选了）** | 每个 lr 取"两温度平均 dev 准确率"最高的 epoch；选这个平均值最高的 lr；平手取小 lr |
| 只看 T=0.1 | 偏向低温解码的效果 |
| 只看 T=1 | 更接近 RL rollout 的设置（rollout 用 T=1） |
| 三个 lr 都跑消融 | 不用选，但多约 1.7 小时 GPU |

推荐两温度平均的理由：
1. D14 定了两个温度都报告，只看一个会偏向那一个；T=1 关系到 RL 的探索，T=0.1 是最好的解码，两边都重要。
2. 两次评测平均，采样噪声比单次小。单次 dev 1000 的标准误约 1.2–1.5pp，几个 lr 之间的差距很可能就在这个量级。
3. 平手取小 lr：离 base 更近、更保守。
4. 规则写在 `code/scripts/summarize_sft.py` 里，在看到结果**之前**就定了。

**已知偏差（报告里要写）**：lr 是在 v1b 上选的，对 v1b 略有利；而且"最好 epoch"本身有赢家诅咒，会高估 v1b。所以 D10 的比较**按同一 lr、同一 epoch 逐个配对**，不拿 v1b 的最好值去比 unfiltered 的最好值。

这次选出的 lr 只用于消融；哪个 SFT checkpoint 作为 RL 起点，之后另外定。

（保留理由，报告「无效 / 放弃的尝试」可用）

| 方案 | 否决理由 | 出处 |
|---|---|---|
| 方向二：从头预训练 | ¥100 只够官方训练量的 2–5%，无法做 benchmark 对比 | 分析 §1.1 |
| 改 MDLM 的 noise schedule 作为改进点 | 连续时间 NELBO 对 schedule 不变，只影响方差，短训练测不出效果 | 分析 §1.1 |
| 换 SMDM-GSM8K / LLaDA-8B 做主模型 | 前者已做过 SFT、成本约 4 倍、无法归因；后者太大 | 分析 §1.4 |
| 用 Dream 等 AR 转来的 DLM | 处于"不能选 AR"规则的灰区 | 分析 §1.4 |
